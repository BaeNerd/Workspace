## 0. 공통 정책

### 0.1 플랫폼 정체성

AX Platform은 콜마그룹 29개 관계사의 자동화·AI 자산을 등록·발견·재사용하는 그룹 공용 카탈로그다. 원칙 세 가지:

- ① 공유 우선 — 등록 문턱은 낮게, 재사용은 쉽게.
- ② 비평가 원칙 — 집계·현황 데이터는 개인·부서·관계사 성과 평가에 쓰지 않으며, 화면 워딩에도 이를 반영한다.
- ③ 질문 중심 — 사용자는 "무엇을 써야 하나"를 묻고, 카탈로그가 답한다(검색·추천·가이드·향후 RAG).

### 0.2 용어·명칭 표준

개별 자산의 사용자 노출 총칭은 "카드"(화면명 "카드 관리" 포함). "항목"은 자산을 지칭하지 않는 축(분류 원소, 설정 필드)에만 사용한다. 노출 묶음 표현은 "자동화·AI 도구". 카테고리 7종 표시명: n8n · Power Automate · 나만의 비서 · AI Model · ML 모델 · Vibe Coding · AI 프로젝트(내부 id: n8n/pa/assistant/ai-orchestration/ml/vibe/etc — 내부 식별자·라우트·값 문자열은 표시명과 분리 관리하며 임의 변경 금지). 개발 용어의 쉬운 치환 표준: 프리필→현재 값 자동 표시, diff→변경분만 저장, 브레드크럼→위치 경로 표시, accessUrl→외부 도구 주소, shortDesc→한 줄 설명. 클라이언트 저장 키 5종: ax_scraps·ax_user_interests·ax_notifications_read·ax_recent_viewed(localStorage), demo_user(sessionStorage — 데모 로그인 유지, SSO 전환 시 제거).

### 0.3 카드 ID

{PREFIX}-{YYYY}-{NNN}, 접두어 7종(N8N/PA/AST/AIO/ML/VIBE/ETC). 카테고리·연도별 순번, 결번 재사용 금지, 승인 전후 불변, 서버 원자 발급(데모는 makeItemId 모사). 게시 카드의 ID는 사용자 화면에 상시 노출하며 표기 위치는 등록 부서 왼쪽, 공용 컴포넌트 CardIdTag 단일 스타일. ID는 문의·공유 시 카드를 특정하는 공식 식별자다.

### 0.4 운영 상태 없음

카드에는 운영 상태 축(사용 가능/준비 중/일부 제한/사용 중지)이 존재하지 않는다. 유일한 가용 표시는 AI Model의 agentAvailability(사용 가능/사용 불가 — 별개 축). 승인 수명주기(승인 대기/부분 승인/게시됨/반려/중지)는 상태와 별개 개념으로 존치한다. 운영 상태를 변경하는 API 엔드포인트는 존재하지 않는다.

### 0.5 관계사 표시 정책

금지는 단 하나: 사용자 카탈로그 화면(카드·상세·등록·수정요청·내현황의 카드 표시)에서 카드에 관계사를 귀속시켜 표시하는 것. 근거 — 관계사 딱지는 "남의 회사 것" 인식과 관계사 간 비교 분위기를 낳아 공유의 심리적 장벽이 된다. 그 외 관계사명 노출은 전부 허용: 그룹 브랜딩(랜딩 마퀴[복원 예정·별도 담당]·소개 콘텐츠), 본인 소속 표시(로그인·Navbar 아바타), 승인 주체 안내(알림), 공지 본문, 그리고 관리자 화면 전역(검토·카드 관리의 OwnerCompanyBadge, 통계·조직 — 관리자는 등록 주체를 알아야 한다). 이 금지를 관계사명 자체를 지우는 룰로 과잉 적용하지 않는다. 데이터 축 두 가지를 구분한다: company(노출 범위 배열 — 비노출 관계사 전용 카드의 목록 게이팅에만 사용, 사용자 미렌더) / ownerCompany(등록 주체 단일 코드 — 관리자 가시성·권한·통계 축, 사용자 미렌더·API는 제공).

### 0.6 권한 모델

역할 3값: user / companyAdmin(관계사 관리자) / admin(전사 관리자) + managedCompanies(companyAdmin의 담당 관계사 코드 배열, 복수 가능). 판정 원칙: 관리 화면의 가시성·조작 권한은 ownerCompany 단일 축(companyAdmin은 ownerCompany ∈ managedCompanies인 건만 — 검토·카드 관리·콕핏 동일 판정). 화면 접근: 검토·카드 관리·대시보드·통계·공지관리 라우트는 companyAdmin 허용(공지관리는 화면에서 전사 전용 안내), 분류·도구관리·조직·사용자 관리는 전사 전용. 서버 검증 책임: 보호 장치 3종(전사관리자 최소 1명 유지·본인 권한 회수 차단·companyAdmin 담당 관계사 최소 1곳)과 모든 가시성 필터는 서버에서 재검증한다(클라이언트 필터는 데모 한정). 보조 플래그 isGroupViewer(그룹 전체보기 — 비노출 관계사 카드 열람, 부여 시 사유 필수). AI Model 카드의 등록·수정은 admin 전용.

### 0.7 병렬 2-슬롯 승인

신청 1건에 관계사 슬롯 + 전사 슬롯. 관계사 슬롯은 신청 등록 주체(ownerCompany) 담당 companyAdmin(또는 admin), 전사 슬롯은 admin 전용. 두 슬롯 승인 완료 시 게시. 어느 슬롯이든 반려 가능(사유 필수). 승인 취소: 게시 전(부분 승인)까지, 본인 권한 슬롯만, 확인 절차 후 슬롯 대기 복귀 — 이력에는 approve/reject/cancel 3종 액션이 남는다. 서버 요건: 슬롯 갱신 + 이력 기록 + 2/2 게시 전환 판정은 단일 트랜잭션, 동시 승인 경합은 잠금으로 직렬화.

### 0.8 예상 절감 시간

입력은 수치 + 주기(일/주/월/년), 직렬화 표준 "<주기> N시간". 집계는 연간 환산(일 365 / 주 52 / 월 12 / 년 1), 원본 텍스트 보존, 환산 불가 값은 부풀리지 않고 "추정 불가"로 분리 표기한다 — 경영 보고 수치의 신뢰는 이 정직함에서 나온다. 적용 카테고리는 자동화 계열(n8n·PA) 중심. 랜딩은 절감 수치를 노출하지 않는다(절감 집계는 관리자 통계 전용).

### 0.9 데이터·집계 공통 원칙

- ① 총량 일치: 랜딩·목록·통계·대시보드의 카드 총량은 단일 카탈로그 SSOT에서 파생되어 항상 일치한다(현 데모 50건). 통계는 statsDerive 순수 함수군이 카탈로그에서 직접 계산하며 별도 합성 수치를 두지 않는다.
- ② 조회수(views)는 인기 정렬·트렌딩의 소스일 뿐 성과 지표·통계 축이 아니다(서버 집계 전환 예정).
- ③ 승인·수정 요청 body에 노출 범위 company를 포함하지 않는다.
- ④ 목업 정합 규칙: 동일 ID·상이 내용 금지, 유령 ID 참조 금지, 상세가 SSOT.

### 0.10 개인화 3축

스크랩(useScraps)·관심사(useInterests — 관심 카테고리·도메인 → 랜딩 추천 매칭)·알림(useNotifications — kind 7종, 공지는 알림을 발생시키지 않는다, 발송 트리거는 서버 책임: 승인·반려·취소·수정요청 처리 시점). 세 훅 모두 localStorage + useSyncExternalStore로 전 화면 실시간 동기화. 백엔드 계약: scraps PUT/DELETE 멱등, notifications GET/PATCH, me/interests PUT.

### 0.11 디자인·레이아웃 표준

색은 styles/tokens.ts 단일 소스(랜딩 기준 파스텔 톤 — 중립·주조색 토큰), 의미색(카테고리·승인 상태·신호색·알림 kind)은 정보 축으로서 토큰 통일 대상에서 제외한다. 레이아웃 폭은 styles/layout.ts: 사용자 CONTENT_MAX_WIDTH 1400 / 폼 760, 관리자 ADMIN_CONTENT_MAX 1320 · 마스터 패널 300 · 좌우 패딩 32(9화면 공통). 성장형 목록은 "더보기 (남은 N건)" 증분 패턴(useVisibleCount + LoadMoreButton)으로 통일한다. 신규 화면·수정 시 이 표준을 따르며 개별 리터럴 도입을 금지한다.

## PART 1. 사용자 화면

### USR-00 랜딩 (LandingPage, /) — 공개

**정의·역할**: 플랫폼 진입 첫 화면. 카탈로그 탐색의 시작점이자 개인화 정보(스크랩·추천·알림)의 요약 허브.

**목적**: 방문 즉시 플랫폼에 어떤 자산이 있는지 보여주고, 탐색·등록·가이드로 자연스럽게 연결한다.

**기획 의도**: 개인화 패널을 프로모션 배너와 함께 최상단에 배치해, 재방문 사용자가 자신의 이용 맥락(스크랩한 카드, 맞춤 추천, 알림 현황)을 바로 이어서 확인할 수 있도록 설계했다. 추천은 사용자가 설정한 관심 카테고리·도메인과 일치하는 카드 중 조회수·좋아요 상위를 제시하며, 관심사 미설정 사용자에게는 임의 추천 대신 설정 안내를 제공해 추천 품질에 대한 신뢰를 유지한다.

**화면 동작**

- ① 프로모션 배너(5초 자동 전환, 클릭 시 해당 카테고리 목록 이동) + 개인화 패널(스크랩 N개 → 스크랩 필터 목록, 맞춤 추천, 알림 최근 3건, 퀵메뉴: 등록 현황·설정·카드 등록·로그아웃)
- ② 히어로(회전 헤드라인, 검색, 카테고리 7타일)
- ③ 플랫폼 현황(총 카드 수 카운터, 카테고리별 막대, 전체 카드 보기)
- ④ 인기 카드(카테고리 필터, 좋아요 상위 6)
- ⑤ 최신소식(종류 탭, 더보기 → 소식 화면) + 실시간 인기 카드(조회수 상위 5)
- ⑥ 업무별 카드(도메인 필터)
- ⑦ CTA 4종(둘러보기 / AI Model / 이용 가이드 / 문의 채널 — Teams 새 창)

카드에는 스크랩 토글과 카드 ID(CardIdTag)를 표시한다.

**지켜야 할 룰**: 카드에 관계사 귀속 표시를 하지 않는다(0.5). 절감 시간 수치를 노출하지 않는다(0.8 — 절감 집계는 관리자 통계 전용). 총 카드 수는 카탈로그 단일 소스에서 파생되어 목록·통계와 항상 일치한다(0.9). 비로그인 상태에서도 열람 가능하며, 로그인 여부에 따른 차이는 인사말뿐이다.

**화면 구조**

```
랜딩 ├─ 프로모션 배너 + 개인화 패널 ├─ 히어로(검색·카테고리 타일)
     ├─ 플랫폼 현황 ├─ 인기 카드 ├─ 최신소식 + 실시간 인기
     ├─ 업무별 카드 ├─ CTA 4종
```

**개발 연동 노트**: getAssetItems·getNotices·getMonthlyNewCount, 훅 useScraps·useInterests·useNotifications. 추천 로직(관심사 매칭 후 조회수·좋아요 상위 12)은 연동 시 서버 추천 API 대체 후보. 조회수는 서버 집계 전환 대상(0.9). PartnerMarquee(관계사 로고 마퀴)는 별도 담당자가 복원 예정.

### USR-01 로그인 (LoginPage, /login) — 공개

**정의·역할**: 그룹 SSO 로그인 진입점. 데모 단계에서는 역할별 데모 계정을 함께 제공한다.

**목적**: 실서비스는 Microsoft SSO 단일 동선으로 운영하고, 데모 단계에서는 권한별 시나리오(user·companyAdmin·admin)를 시연할 수 있게 한다.

**기획 의도**: SSO 버튼을 기본 동선으로 상시 노출하고 데모 계정은 접이식 보조 영역으로 분리해, 실서비스 전환 시 화면 구조 변경을 최소화한다. companyAdmin 데모 계정을 단일 담당·복수 담당 2종으로 구성한 것은 담당 관계사 기준 가시성 필터의 동작 차이를 시연하기 위함이다.

**화면 동작**: SSO 로그인 버튼(데모에서는 관리자 계정으로 처리) / 접이식 데모 계정 6종 선택 / 지원 문의 메일 링크. 로그인 후 admin·companyAdmin은 관리자 화면으로, user는 원래 이동하려던 화면으로 이동한다.

**지켜야 할 룰**: 데모 영역에 "실제 배포 시 제거" 안내를 유지한다. 데모 계정의 소속·담당 관계사 표시는 허용 범위다(0.5). 하단에 "사내 전용 플랫폼 · 외부 접근 불가" 고지를 유지한다.

**화면 구조**: 브랜드 → SSO 버튼 → 접이식 데모 계정 → 지원 링크 → 고지.

**개발 연동 노트**: getManagedCompanies(email) — 연동 시 GET /auth/me의 managedCompanies로 대체. 인증은 Azure AD OIDC → 백엔드 JWT(0.6). 데모 세션 키(demo_user)는 SSO 전환 시 제거된다.

### USR-03 카탈로그 목록 (ProjectListPage, /projects) — 로그인 필요

**정의·역할**: 전체 카드의 탐색·필터 화면. 플랫폼의 중심 동선.

**목적**: 카테고리·도메인·태그·검색·스크랩 축을 조합해 필요한 카드를 빠르게 찾는다.

**기획 의도**: 필터 영역을 화면 상단에 고정(sticky)해 스크롤 중에도 탐색 조건을 유지·변경할 수 있게 했다. 스크랩 목록은 별도 화면 대신 목록의 필터 토글로 제공해 탐색 문맥을 유지하면서 구현을 단순화했다. 초기화 버튼은 카테고리·도메인·스크랩 필터만 해제하고 검색어·정렬은 보존한다 — 사용자가 직접 입력한 조건과 클릭형 필터를 구분해 다루기 위한 의도된 동작이다.

**화면 동작**: 헤더 검색 / 필터 1행: 카테고리 세그먼트(전체+7)·도메인, 2행: 인기 태그 상위 6 토글·"스크랩 N" 토글·초기화 / 본문: 결과 수·정렬(최신/인기/이름)·카드 그리드(24개 단위 더보기). 카드 구성: 카테고리 pill·제목·요약·카드 ID+등록 부서·조회수·좋아요·스크랩 토글(AI Model 카드는 강점 3개와 비용 뱃지 표시). URL 파라미터 q·platform·domain·scrap을 수신해 초기 상태를 구성한다.

**지켜야 할 룰**: 카드에 관계사 귀속 표시를 하지 않는다. company(노출 범위)는 비노출 관계사 전용 카드의 목록 제외 판정에만 사용하며, 그룹 전체보기 권한자는 예외적으로 열람 가능하고 상단에 안내 뱃지를 표시한다. 카드 ID는 등록 부서 왼쪽에 상시 표시한다(0.3).

**화면 구조**: 헤더(검색) → 고정 필터 2행 → 결과 수·정렬 → 카드 그리드 → 더보기.

**개발 연동 노트**: getAssetItems·getOrgCompanies(노출 관계사 판정). 연동 시 필터·정렬·페이지 파라미터는 서버 처리(GET /assets), 노출 게이팅·그룹 전체보기 판정은 서버에서 재검증한다(0.6).

### USR-04 카드 상세 (AssetItemDetailPage, /{카테고리}/:itemId) — 로그인 필요

**정의·역할**: 카드 1건의 상세 정보와 소통(활용 후기·게시판·담당자 연락)을 제공하는 화면.

**목적**: 카드의 활용 가능 여부, 사용 방법, 문의처를 한 화면에서 확인할 수 있게 한다.

**기획 의도**: 7개 유형은 정보 구조가 서로 달라, 탭 구성을 유형별로 다르게 한다(상세 탭 라벨: n8n=상세 동작, Power Automate=플로우 정보, 나만의 비서=비서 구성, AI Model=모델 사양, ML=모델 정보 / Vibe Coding·AI 프로젝트는 상세 탭 없이 개요에 통합). 좋아요·스크랩·담당자 연락·수정 요청을 헤더 액션으로 모아 확인에서 행동으로 이어지는 동선을 짧게 유지한다.

**화면 동작**: 위치 경로 표시 → 헤더(카테고리 pill, AI Model은 가용 뱃지·제공사, 제목·요약, 액션: 좋아요·스크랩·담당자 연락·수정 요청·[AI Model] 모델 접속) → 메타 행(카드 ID 최선두·등록 부서·최종 수정일) → 탭(개요 / [유형별 상세] / 담당자 / 업데이트&논의 N). 개요 탭은 이미지 캐러셀·설명·활용 후기(등록 가능), 논의 탭은 게시글(태그: 공지·Q&A·이슈제보·건의, 좋아요, 더보기 증분). 방문 시 최근 조회 기록을 저장한다(상위 10건).

**지켜야 할 룰**: 관계사 귀속을 표시하지 않는다(등록 주체 데이터는 API로 제공하되 사용자 화면에는 렌더하지 않음 — 0.5). 수정 요청은 게시 카드에 대해 누구나 신청할 수 있다(담당자 변경 등 제3자가 발견하는 수정 사유가 많은 점을 반영). AI Model의 모델 접속 URL은 카드 실행 URL을 두지 않는 원칙의 유일한 예외다.

**화면 구조**: 위치 경로 → 헤더(액션) → 메타 행 → 유형별 탭 → Footer.

**개발 연동 노트**: getAssetItem·getReviewsByItem·getPostsByItem·getFallbackN8nWorkflowJson. 연동 시 좋아요는 PUT/DELETE 멱등, 후기·게시글은 POST, 조회수는 서버 집계. 후기 등록 시 알림(후기등록)은 서버가 발송한다(0.10).

### USR-05 신규 등록 신청 (ProjectRegisterPage, /projects/new) — 로그인 필요

**정의·역할**: 카드 등록 신청 폼. 유형 선택 → 정보 입력 → 최종 확인의 3단계.

**목적**: 등록 부담을 낮추면서 승인 검토에 필요한 정보를 유형별 최소 필수로 수집한다.

**기획 의도**: 입력 단계를 3단계로 최소화해 등록 진입 장벽을 낮춘다. 유형별 입력 항목은 실제로 사용하는 축만 구성한다(난이도=n8n, 비용·컨텍스트=AI Model, 모델 유형=ML) — 사용하지 않는 입력 항목은 관리 부담이 되므로 두지 않는다(분류 관리와 동일 원칙). AI Model 유형의 등록은 관리자 전용으로 제한한다 — 모델 카탈로그는 운영 측이 선별·관리하는 영역으로 정의했다.

**화면 동작**: Step0 유형 카드 7종(비관리자에게는 AI Model 미노출) → Step1 기본 정보(사진 최대 10장, 제목, 한 줄 요약, 상세 설명, 업무 도메인, 태그) + 유형별 섹션(n8n은 워크플로우 JSON 업로드·미리보기 포함) + 예상 절감 시간(수치+주기 선택) + 담당자(복수 등록 가능) → Step2 입력 요약 확인과 ID 발급 안내("접수 시 {PREFIX}-{연도}-순번 형식의 고유 ID 발급") → 제출 후 내 현황으로 이동.

**지켜야 할 룰**: 노출 범위(관계사) 입력 항목을 두지 않는다 — 신규 카드는 전사 공용이다(0.9). 예상 절감 시간은 표준 형식으로 직렬화한다(0.8). 태그는 자유 입력을 허용하며, 누적된 자유 태그는 관리자가 고정 분류로 표준화한다(ADM-05).

**화면 구조**: 단계 표시 → Step0 유형 선택 → Step1 정보 입력(공통+유형별+담당자) → Step2 확인·제출.

**개발 연동 노트**: 공용 컴포넌트 ImageCarouselInput·TimeSavedInput·ChipInput, 공유 상수 ML_TYPES. 제출은 등록 신청 API(POST), 카드 ID는 서버에서 원자적으로 발급(0.3), 접수 알림(신청접수)은 서버가 발송(0.10). 이미지 업로드 스토리지는 선정 대기(부록 B).

### USR-06 수정 요청 (EditRequestPage, /edit-request/:id) — 로그인 필요

**정의·역할**: 게시된 카드의 수정을 신청하는 단일 폼. 대상 카드의 현재 값을 자동으로 표시한 상태에서 편집한다.

**목적**: 담당자 변경, 내용 갱신 등 게시 이후의 변경 사항을 관리자 검토를 거쳐 게시본에 반영한다.

**기획 의도**: 게시본은 전사가 참조하는 공유 자산이므로 직접 수정 대신 요청-검토 구조를 둔다. 신청 자격을 등록자로 한정하지 않는 것은, 담당자 퇴사·이관처럼 제3자가 발견하는 수정 사유가 실무에서 많다는 점을 반영한 것이다. 폼 구성은 등록 폼과 동일한 편집 항목에 "수정 사유"만 추가해, 별도의 입력 방식을 학습할 필요가 없게 한다.

**화면 동작**: 대상 카드(:id)의 전 필드를 현재 값으로 자동 표시(존재하지 않는 ID는 안내 문구) → 대상 배너(카드 ID·유형·제목) → 기본 정보·유형별 섹션(대상 카드의 유형을 따름)·담당자 편집 → 수정 사유(필수) → 취소/제출. 진입 경로는 2곳: 카드 상세 헤더의 "수정 요청", 내 현황의 게시됨 카드.

**지켜야 할 룰**: AI Model 카드의 수정은 관리자 전용이며, 비관리자 진입 시 안내를 표시한다(0.6, 등록 제한과 동일 원칙). 수정 사유 없이 제출할 수 없다. 노출 범위(company)는 요청 데이터에 포함하지 않는다(0.9).

**화면 구조**: 위치 경로 → 대상 배너 → 편집 폼(공통+유형별+담당자) → 수정 사유 → 취소/제출.

**개발 연동 노트**: getAssetItem(:id)로 현재 값 구성. 제출은 수정 요청 API(POST, 사유 포함), 처리 결과 알림(수정요청처리)은 서버가 발송(0.10). 관리자 측 처리 큐 화면은 미구현으로, API 계약(조회 GET·처리 PATCH)을 명세서에서 먼저 확보한다(부록 B).

### USR-07 내 현황 (MyStatusPage, /my-status) — 로그인 필요

**정의·역할**: 본인 등록 신청의 승인 진행 상황과 본인이 작성한 후기를 확인하는 개인 현황 화면.

**목적**: 신청 건이 승인 절차의 어느 단계에 있는지 단계 축으로 명확히 보여준다.

**기획 의도**: 병렬 2-슬롯 승인 구조(0.7)를 사용자에게 그대로 시각화한다(신청 완료 → 관계사/전사 승인 → 게시 완료 인디케이터). 진행 상황을 투명하게 공개해 문의 부담을 줄이고, 반려 시에는 검토자가 작성한 사유를 그대로 표시해 결과에 대한 이해를 돕는다.

**화면 동작**: 5개 탭 KPI(전체·승인 대기·부분 승인·게시됨·반려) → 신청 카드 목록(카드 ID 최선두, 카테고리 pill, 제목·요약, 단계 뱃지, 신청/처리일, 병렬 승인 인디케이터, 반려 사유 박스)과 더보기 증분. 카드별 액션: 내용 확인/접기, 신청 취소(대기 상태), 수정 요청(게시됨 → USR-06), 신청 삭제(반려 상태, 확인 절차 포함). 게시됨 카드 클릭 시 상세로 이동. 하단에 "내가 남긴 후기" 목록.

**지켜야 할 룰**: 승인 단계 명칭은 0.7 표준(승인 대기/부분 승인/게시됨/반려/중지)을 따른다. 삭제는 반려 건에 한하며 복구 불가를 고지한다. 관계사 귀속을 표시하지 않는다(0.5).

**화면 구조**: 헤더 → 5탭 KPI → 신청 카드 목록(+더보기) → 내가 남긴 후기.

**개발 연동 노트**: getMyApplications·getMyReviews·deriveStage. 연동 시 본인 소유 필터와 신청 취소·삭제의 상태 전이 검증은 서버 책임(0.7의 이력 체계와 동일).

### USR-08 공통 내비게이션 (Navbar / Footer / AdminNavbar / NotificationBell)

**정의·역할**: 전 화면 공통의 이동·알림·계정 영역.

**목적**: 어느 화면에서든 탐색·등록·알림·설정에 일관된 방식으로 접근할 수 있게 한다.

**기획 의도**: 상단 메뉴는 핵심 동선 3개(이용 가이드 · AX 플랫폼 · AX 카드 등록)로 최소 구성한다. 알림 벨은 사용자·관리자 내비게이션 양쪽에 동일하게 배치해 승인 진행 통지가 역할과 무관하게 도달하도록 한다. 아바타 드롭다운에 본인 소속 관계사를 표시해(0.5 허용 범위) 다관계사 환경에서 로그인 계정을 확인할 수 있게 한다.

**화면 동작**: Navbar — 브랜드 → 메뉴 3종 → (관리자 역할 시) 관리자 진입 → 알림 벨(미읽음 뱃지, 드롭다운 최근 5건·전체 읽음·클릭 시 해당 카드로 이동) → 역할 pill → 아바타 드롭다운(소속 관계사[companyAdmin은 담당 병기], 내 등록 현황, 설정, 관리자 페이지, 로그아웃). Footer — 브랜드와 "사내 전용 플랫폼 · 외부 접근 불가" 고지(링크 없음). AdminNavbar — 브랜드·알림 벨·관리자 pill·로그아웃.

**지켜야 할 룰**: 알림에서 카드로의 이동 경로는 카드 ID 접두어에서 파생한다(특정 목업 데이터에 의존하지 않음). 공유 모드에서는 알림 벨을 표시하지 않는다.

**화면 구조**: Navbar(메뉴·벨·계정) / Footer(브랜드·고지) / AdminNavbar / NotificationBell(공용).

**개발 연동 노트**: useNotifications·orgCompanyName·detailPathForItemId. 연동 시 알림 조회 GET·읽음 PATCH(0.10). 카테고리 외부 환경 진입 UI(외부 도구 주소 accessUrl의 소비 지점)는 미구현이며 백로그로 관리한다(부록 B).

**지켜야 할 룰**: 승인 안내 서술은 0.7 정책과 일치를 유지한다(정책 변경 시 동기화 대상). 정적 콘텐츠로 개인화·권한 분기가 없다.

**화면 구조**: 히어로 → 왜 AX Platform → 시작하기 → 등록 → 승인 → FAQ.

**개발 연동 노트**: 정적 콘텐츠(모듈 레벨 정의). 서버 연동 불필요. 콘텐츠 개정은 코드 배포를 수반한다.

**기획 의도**: 종류 2탭(공지사항/업데이트)과 고정 우선 정렬의 단순 구조로 구성한다. 랜딩의 최신소식 영역과 동일한 단일 소스를 사용하므로 두 화면의 내용이 항상 일치한다.

**개발 연동 노트**: getNotices(kind). 연동 시 공개 조회 API(노출 필터 서버 적용).

## PART 2. 관리자 화면

**PART 2 공통**: 관리자 화면은 AdminNavbar + 좌측 AdminSidebar의 콘솔 레이아웃을 사용한다. 콘텐츠 폭은 관리자 표준(ADMIN_CONTENT_MAX 1320, 마스터 패널 300, 좌우 패딩 32 — 0.11)을 따른다. 사이드바의 승인 대기 건수는 조회 범위 선택과 무관하게 본인 권한 기준(baseScope)으로 고정 표시한다. 접근 권한은 0.6의 화면 접근 기준을 따른다.

### ADM-01 대시보드 (AdminDashboard, /admin) — admin·companyAdmin

**정의·역할**: 관리자의 시작 화면. "지금 처리할 일"과 최근 변화를 요약하는 운영 콕핏.

**목적**: 승인 대기·수정 요청 등 처리 대기 업무를 한눈에 확인하고, 해당 관리 화면으로 바로 진입한다.

**기획 의도**: 대시보드와 통계의 역할을 질문 축으로 분리했다 — 대시보드는 "지금 처리할 것이 있는가"(운영), 통계는 "잘 확산되고 있는가"(분석)에 답한다. 이에 따라 분석성 차트(등록 추이·카테고리 분포 등)는 통계로 일원화하고, 대시보드의 모든 위젯은 해당 관리 화면으로의 진입점 역할을 겸한다. 기간 필터를 두지 않는 것도 같은 이유다 — 현재 시점의 스냅숏 화면이기 때문이다.

**화면 동작**: 헤더(조회 범위 선택기 — admin은 선택, companyAdmin은 담당 범위 뱃지) → KPI 3종(총 카드 수 · 이번 달 신규 · 승인 대기 총계[부분 승인 건수 병기]) → 처리 대기 행: 승인 대기 큐 상위 5건(카드 ID·제목·단계 칩·등록 관계사 뱃지, 클릭 → 등록 신청 검토) · 수정 요청 대기(건수와 최근 건, 클릭 → 검토 화면) → 현황 행: 최근 게시된 카드(클릭 → 카드 관리) · 최근 활동(후기·게시글 최신 5건, 클릭 → 해당 카드 상세) → "상세 분석은 통계에서 보기" 링크.

**지켜야 할 룰**: 기간 필터를 두지 않는다(고정 스냅숏). 위젯별 고정 기준 — 누적 지표는 전체 기간, 이번 달 신규는 당월 실측. companyAdmin의 모든 위젯 수치는 등록 관계사(ownerCompany) 기준 담당 범위의 부분집합으로 표시한다(0.6). 담당 관계사 미지정 companyAdmin에게는 안내 배너를 표시한다.

**화면 구조**: 헤더(조회 범위) → KPI 3종 → 처리 대기(승인·수정 요청) → 현황(최근 게시·최근 활동) → 통계 링크.

**개발 연동 노트**: getDashboardData(scope) — 검토 큐·카탈로그·활동 피드 파생. 연동 시 별도 집계 API 대신 기존 자원 조합(검토 큐 조회·카드 최신 조회·활동 피드)으로 구성 가능한지 명세서에서 판단(활동 피드는 GET /activity 후보). 가시성 필터는 서버 재검증(0.6).

### ADM-02 등록 신청 검토 (AdminReview, /admin/review) — admin·companyAdmin

**정의·역할**: 등록 신청의 검토·승인·반려 화면. 병렬 2-슬롯 승인의 실행 지점.

**목적**: 신청 내용을 확인·보완한 뒤 관계사/전사 슬롯을 승인하거나 사유와 함께 반려한다.

**기획 의도**: 검토 중 내용 편집을 허용한다 — 오탈자나 경미한 보완 때문에 반려-재신청을 반복하는 비용을 줄이기 위함이다. 승인 취소를 게시 전까지 허용하는 것은 실수 복구 경로 확보 목적이다: 병렬 구조에서는 한 슬롯의 오승인 후 상대 슬롯이 승인되면 즉시 게시되므로, 게시 전에 되돌릴 수단이 필요하다. companyAdmin에게는 담당 관계사가 등록 주체인 신청만 표시한다 — 승인 자격이 없는 건이 목록에 보이면 권한 구조에 대한 혼란을 낳기 때문이다.

**화면 동작**: 좌측 목록 — 요약 칩 4종(전체·승인 대기·부분 승인[관계사만/전사만 세분]·처리완료)·유형 필터·신청 행(카테고리·단계·등록 관계사 뱃지·제목·부서·슬롯 표시)·더보기 증분 / 우측 상세 — 승인 이력, 편집 가능 안내("내용을 직접 수정한 후 승인할 수 있습니다"), 기본 정보·유형별·담당자 편집, 슬롯 카드 2개(승인/승인 취소)·반려(사유 필수, "신청자에게 그대로 전달됩니다" 안내).

**지켜야 할 룰**: 가시성·승인 자격은 등록 관계사(ownerCompany) 단일 축 — companyAdmin은 담당 관계사 등록 건만 보이고, 그 건의 관계사 슬롯만 승인할 수 있다. 전사 슬롯은 admin 전용. 승인 취소는 게시 전·본인 권한 슬롯만, 확인 절차 후 대기 복귀(0.7). 반려는 어느 슬롯 권한자든 가능하며 사유가 필수다.

**화면 구조**: 좌 신청 목록(요약 칩·필터·행) / 우 상세(이력 → 편집 폼 → 슬롯 2개·반려).

**개발 연동 노트**: getReviewQueue·deriveStage. 연동 시 큐 조회는 companyAdmin 필터를 서버 적용, 승인·취소·반려는 슬롯 갱신+이력(approve/reject/cancel)+게시 판정 단일 트랜잭션(0.7). 승인·반려·취소 각각 알림 발송 트리거(0.10).

### ADM-03 카드 관리 (AdminProjectManage, /admin/projects) — admin·companyAdmin

**정의·역할**: 게시된 전체 카드의 관리 화면(조회·수정·삭제·직접 등록).

**목적**: 게시본의 품질 유지 — 내용 수정, 이미지 관리, 부적절 카드 삭제, 관리자 직접 등록.

**기획 의도**: 좌측 목록을 카테고리 그룹 아코디언으로 구성해(기본 접힘, 검색 시 자동 펼침) 카드 수가 늘어도 목록 길이가 관리 가능하게 유지한다. 편집 항목은 등록 폼과 동일 체계(이미지 편집 포함)로 맞춰 두 화면 간 학습 비용을 없앤다. 권한은 세분화한다 — 수정·직접 등록은 admin 전용, 삭제는 담당 범위 내 companyAdmin에게도 허용해 관계사 차원의 품질 관리를 가능하게 한다.

**화면 동작**: 좌측 — 전체 카드 수·직접 등록(admin)·검색·유형 칩·카테고리 그룹 아코디언(그룹 헤더: 색 dot·카테고리명·건수)·행(제목·카드 ID·부서·등록 관계사 뱃지) / 우측 — 미선택 시 총 건수·카테고리 분포 안내, 선택 시 헤더(수정[admin]·삭제)·기본 정보(수정 모드에서 이미지 추가/삭제 포함)·유형별·등록 신청자 정보·담당자.

**지켜야 할 룰**: 관리 가시성·삭제 권한은 등록 관계사(ownerCompany) 축 — 검토 화면과 동일 판정(0.6). 수정·직접 등록은 admin 전용. 삭제는 확인 절차와 복구 불가 고지. 직접 등록 시에도 카드 ID 발급 규칙(0.3)을 따른다.

**화면 구조**: 좌 목록(검색·필터·카테고리 아코디언) / 우 상세·편집(이미지·유형별·신청자·담당자).

**개발 연동 노트**: getManagedAssetItems(카탈로그 파생). 연동 시 수정 PATCH·삭제 DELETE·직접 등록 POST, 권한 검증 서버 책임. 이미지 업로드는 스토리지 선정과 연동(부록 B).

### ADM-04 통계 (AdminStatistics, /admin/statistics) — admin·companyAdmin

**정의·역할**: 등록·활용 현황의 기간 분석 리포트. 운영 성과 보고의 근거 자료.

**목적**: 카탈로그의 확산 추이와 절감 효과를 기간·범위를 바꿔가며 정량으로 확인한다.

**기획 의도**: 모든 수치를 카탈로그 단일 소스에서 파생해(0.9) 랜딩·목록과 총량이 항상 일치하게 한다 — 화면 간 수치 불일치는 보고 자료의 신뢰를 해치기 때문이다. 절감 시간은 연간 환산하되 환산 불가 값은 "추정 불가"로 분리 표기한다(0.8). 분석 축은 실제 입력받는 데이터에만 둔다(난이도=n8n, 비용=AI Model, 모델 유형=ML). 부서·도메인 차트는 상위 5 기본 표시 + 전체 펼치기로 구성한다 — SSO 연동 후 부서 수가 크게 늘어날 상황에 대비한 구조다.

**화면 동작**: 헤더(조회 범위 선택기 + 기간 프리셋: 최근 3개월/최근 6개월/올해 전체[기본]/범위 지정[시작~종료 월, 최대 24개월]) → 요약 카드 4종(전체 등록물·이번 달 신규·참여 부서·참여 관계사) → 등록 추이(카테고리 스택, 선택 기간 연속 표시) → 카테고리별 현황 → 도메인·부서(상위 5 + "전체 보기 (N)" 펼치기) → 절감 효과 3종 세트(연간 환산·집계 가능·추정 불가) → 난이도/비용/모델 유형 분석 → 후기 상위 5 → 태그 빈도.

**지켜야 할 룰**: 기간 프리셋 4종 고정, 범위 지정 최대 24개월(서버도 재검증). 전 기간 프리셋은 두지 않으며 과거 데이터는 범위 지정으로 조회한다. 운영 상태 축·검색 키워드 축을 두지 않는다(키워드 측정은 백로그). 집계는 성과 평가 용도가 아님을 화면 문구에 유지한다(0.1). companyAdmin은 담당 범위 기준으로 집계된다.

**화면 구조**: 헤더(범위·기간) → 요약 4카드 → 등록 추이 → 카테고리 현황 → 도메인·부서(상위 5) → 절감 효과 → 3축 분석 → 후기·태그.

**개발 연동 노트**: getStatsByScope(scope, range)·statsDerive 함수군 — 이 함수 목록이 통계 API 계약의 기준(GET /stats/*, ?company=&from=YYYY-MM&to=YYYY-MM). 절감 환산 규칙(parseTimeSaved)은 서버 이관 시 동일 유지. 검증 기준: 현 데모 총량 50 전 축 일치.

### ADM-05 분류체계 관리 (AdminTaxonomy, /admin/taxonomy) — admin 전용

**정의·역할**: 고정 분류(업무 도메인·구성 난이도·비용 등급·ML 모델 유형)와 자유 태그의 관리 화면.

**목적**: 검색·필터·통계의 축이 되는 분류 값을 표준화하고 자유 태그의 누적을 관리한다.

**기획 의도**: 분류는 고정 분류 위주로 운영한다 — 검색·필터·통계, 향후 RAG까지 통제된 어휘가 있어야 품질이 유지된다. 자유 태그는 등록 문턱을 낮추는 보조 수단이며, 반복 사용되는 태그를 관리자가 고정 분류로 편입하는 운영 순환을 상정한다. 편입 대상은 실제 입력 축이 있는 분류로 제한한다(AI Model 태그 → 비용 등급, ML 태그 → 모델 유형) — 대응 축이 없는 분류로의 편입은 데이터 정합을 해치기 때문이다.

**화면 동작**: 고정 분류 4탭(값 목록·사용 건수·추가/수정/삭제[확인 절차]) + 자유 태그 탭(누적 건수 표시) — 출처 카테고리 필터·태그 행(사용 N건·제안자·사용 카드)·선택 삭제·고정 분류 편입(대상 분류 선택 → 확정)·더보기 증분. 우측에 운영 유의사항 안내.

**지켜야 할 룰**: 고정 분류 삭제 시 해당 분류가 지정된 기존 카드는 공란 처리될 수 있음을 안내한다(참조 무결성 정책은 서버에서 일관 적용). 자유 태그 출처는 7개 카테고리 전체에 대응한다. 편입 가능 조합은 위 2종으로 제한한다.

**화면 구조**: 분류 탭 4종 + 자유 태그 탭 → 좌 값/태그 목록 → 우 추가·편입 패널·운영 유의사항.

**개발 연동 노트**: getCategoryTaxonomy·getFreeTags. 연동 시 분류 마스터 테이블 + 카드-분류 참조, 삭제 시 공란 처리 정책 서버 일관 적용, 편입은 태그 → 분류 값 전환과 카드 참조 갱신을 함께 처리.

### ADM-06 자동화·AI 도구 관리 (AdminCategories, /admin/platforms) — admin 전용

**정의·역할**: 카테고리 7종의 메타 정보(식별자·표시명·설명·라우트 경로·외부 도구 주소·아이콘·색·노출 상태)를 관리하는 화면.

**목적**: 카테고리 명칭·브랜딩 변경과 신규 카테고리 추가를 운영 단계에서(연동 후 배포 없이) 처리할 수 있게 한다.

**기획 의도**: 카테고리 메타는 단일 소스(CATEGORIES)이며 목록 필터·뱃지·통계 범례가 전부 여기서 파생된다 — 이 화면의 편집이 전 화면에 파급되므로 전사 관리자 전용으로 제한한다. 아이콘(21종)·색(파스텔 프리셋 8종)은 프리셋 안에서 선택하게 해 톤앤매너 일관성을 유지하고, 카테고리 간 유사색 배정을 피한다(뱃지·범례 구분 목적). 삭제보다 비활성화를 권장한다 — 기존 카드의 참조를 보존하기 위함이다.

**화면 동작**: 좌측 카테고리 목록(아이콘·표시명·비활성 뱃지·내부 id) / 우측 상세·편집 — 기본 정보(식별자[신규만 입력 가능]·표시명·한 줄 설명), 경로·연결(라우트 경로·외부 도구 주소), 표시 스타일(아이콘 선택기·색 프리셋·뱃지 미리보기), 노출 상태 토글, 추가/수정/비활성화/삭제(확인 절차). 식별자 형식(소문자·숫자·하이픈)과 id·경로 중복을 검사한다.

**지켜야 할 룰**: 내부 식별자는 생성 후 변경 불가. 신규 추가 시 중복 검사 통과 필수. 외부 도구 주소(accessUrl)는 미설정 허용("미설정" 표기) — 사용자 화면의 소비 지점은 미구현으로 백로그 관리(부록 B).

**화면 구조**: 좌 카테고리 목록 / 우 기본 정보 → 경로·연결 → 표시 스타일 → 노출 상태 → 액션.

**개발 연동 노트**: 연동 시 카테고리 마스터 CRUD API. 편집 파급 범위(전 화면 파생)를 고려해 캐시 무효화 전략 필요. 비활성 카테고리의 기존 카드 처리 정책(열람 유지·신규 등록 차단)을 명세서에서 확정.

### ADM-07 부서·조직 관리 (AdminOrg, /admin/org) — admin 전용

**정의·역할**: 관계사 노출, 부서 체계, 관계사 관리자 현황, 문의 채널을 관리하는 조직 운영 화면.

**목적**: 카탈로그의 조직 축(관계사·부서)과 운영 설정을 한 화면에서 관리한다.

**기획 의도**: 4개 섹션으로 구성한다. 관계사 노출 관리는 그룹 내 준비된 관계사부터 단계적으로 플랫폼을 여는 운영 방식을 지원한다. 부서 관리는 SSO(Microsoft Teams/Entra) 연동 동기화를 기본으로 하되 수동 추가를 보조로 둔다 — 조직 개편이 잦은 환경에서 수동 관리만으로는 정합을 유지하기 어렵기 때문이다. 관계사 관리자 현황은 읽기 전용으로 두고 지정·해제는 사용자 관리(ADM-08)로 일원화한다 — 권한 부여 지점이 여러 화면에 있으면 감사 추적이 어려워진다.

**화면 동작**: 섹션1 관계사 노출 관리(관계사별 노출 토글·검색·보유 카드 수 표시) → 섹션2 부서 관리(관계사 아코디언·부서 행 수정/삭제[카드 태깅 시 경고]·수동 추가[중복 검사] + Microsoft Teams 연동 카드: 연동 현황/설정[테넌트·자동 동기화·주기]/미리보기·지금 동기화) → 섹션3 관계사 관리자 현황(읽기 전용, "사용자 관리로 이동" 링크) → 섹션4 문의 채널 설정(Teams 채널 URL 편집·형식 검증) → 운영 유의사항.

**지켜야 할 룰**: 관계사를 비노출로 전환해도 기존 데이터는 삭제되지 않음을 안내한다. 부서 삭제 시 해당 부서로 태깅된 카드 수를 경고한다. 관계사 관리자 지정·해제는 이 화면에서 하지 않는다(ADM-08 소관).

**화면 구조**: 관계사 노출 → 부서 관리(+Teams 연동) → 관계사 관리자 현황(읽기) → 문의 채널 → 유의사항.

**개발 연동 노트**: getOrgCompanies·getOrgDepts·getCompanyAdmins·getTeamsSyncSource·getAssetItemRefs. 연동 시 부서 동기화는 Entra/Teams 디렉터리 API 연계(주기 설정·수동 실행), 문의 채널 URL은 운영 설정 저장 API. 노출 토글은 목록 게이팅(USR-03)과 즉시 정합.

### ADM-08 사용자·권한·로그 관리 (AdminUsers, /admin/users) — admin 전용

**정의·역할**: 관리자 권한 부여·회수, 그룹 전체보기 권한, 등록자 현황, 활동 로그를 관리하는 화면.

**목적**: 권한의 부여·회수를 단일 지점에서 처리하고, 주요 관리 행위를 로그로 추적한다.

**기획 의도**: 권한 편집 지점을 이 화면으로 일원화한다(조직 관리의 현황판은 읽기 전용). 보호 장치 3종을 둔다 — ① 전사 관리자 최소 1명 유지(마지막 1명 회수 차단) ② 본인 권한 회수 차단 ③ companyAdmin의 담당 관계사 최소 1곳 유지. 운영 사고(권한 공백·자기 잠금)를 구조적으로 방지하기 위한 장치이며, 서버에서도 동일 검증한다. 그룹 전체보기 권한은 부여 시 사유를 필수로 받고 확인 절차를 거친다 — 비노출 관계사 카드 열람이라는 예외 권한이므로 부여 근거를 기록으로 남긴다.

**화면 동작**: 4탭 —

- ① 관리자 권한: 전사/관계사 관리자 목록, SSO 사용자 검색, 역할 선택(전사/관계사), 관계사 관리자는 담당 관계사 복수 선택, 부여/회수(보호 장치 적용), 담당 관계사 추가/제거
- ② 그룹 전체보기: 부여 목록, 사유 필수 입력, 확인 절차, 회수
- ③ 등록자 관리: 등록 이력 사용자 테이블(더보기 증분)
- ④ 활동 로그: 카테고리 필터·검색·테이블(더보기 증분)

**지켜야 할 룰**: 보호 장치 3종은 UI와 서버 양쪽에서 적용한다. 권한 부여·회수·그룹 전체보기 변경은 활동 로그에 기록한다. 활동 로그는 소급 수정하지 않는다(감사 무결성).

**화면 구조**: 탭 4종(관리자 권한 / 그룹 전체보기 / 등록자 관리 / 활동 로그).

**개발 연동 노트**: getAdmins·getGroupViewers·getRegistrants·getAuditLogs·getSsoUsers·getSelectableCompanies·getCompanyAdmins. 연동 시 SSO 사용자 검색은 디렉터리 API, 권한 변경은 audit_logs 기록과 단일 트랜잭션, 보호 장치는 서버 재검증(0.6).

### ADM-09 공지·업데이트 관리 (AdminNotices, /admin/notices) — admin 전용(라우트는 companyAdmin 접근 허용, 화면에서 전사 전용 안내)

**정의·역할**: 공지사항·업데이트 소식의 작성·수정·삭제·고정·노출 관리 화면.

**목적**: 랜딩 최신소식과 소식 화면(USR-10)에 게시되는 콘텐츠를 운영한다.

**기획 의도**: 소식은 전사 공지 성격이므로 전사 관리자 전용으로 운영한다(라우트 접근과 화면 안내의 이중 방어). 삭제 대신 노출 끄기를 권장한다 — 일시적으로 감출 소식을 삭제하면 이력이 유실되기 때문이다. 소식은 알림을 발생시키지 않는다(0.10) — 알림은 본인 신청·활동에 대한 통지로 한정해 피로도를 관리한다.

**화면 동작**: 좌측 목록(작성 버튼·종류 필터[전체/공지사항/업데이트]·행: 종류 뱃지·고정/숨김 뱃지·제목·날짜·더보기 증분) / 우측 상세·편집(종류 선택·제목·본문·게시일[형식 검증]·고정/노출 토글[조회 모드 즉시 반영]·저장/삭제[확인 절차, 노출 끄기 권장 안내]). 신규 저장 시 소식 ID(NOTICE-{연도}-{순번}) 발급.

**지켜야 할 룰**: 게시일은 YYYY.MM.DD 형식. 고정 소식은 목록 상단 우선 노출. 노출 꺼진 소식은 사용자 화면에서 보이지 않되 데이터는 유지된다.

**화면 구조**: 좌 소식 목록(필터) / 우 내용 편집 → 노출 설정 → 저장/삭제.

**개발 연동 노트**: getAdminNotices(비노출 포함). 연동 시 공지 CRUD·고정/노출 토글 API, 소식 ID 서버 발급. 공개 조회(USR-10·랜딩)와 관리 조회의 노출 필터 차이를 API에서 구분.

## 부록 A. 데이터 흐름

**A-1 등록 → 승인 → 게시**: 사용자 등록 신청(USR-05, 노출 범위 입력 없음) → 카드 ID 서버 발급(0.3) → 검토 큐 진입(ADM-02, companyAdmin은 등록 관계사 기준 가시성) → 병렬 2-슬롯 승인(관계사=담당 companyAdmin 또는 admin / 전사=admin) → 2/2 완료 시 게시 → 카탈로그(USR-03·04)·랜딩·통계에 반영. 반려 시 사유가 내 현황(USR-07)에 그대로 전달되고, 게시 전에는 슬롯 단위 승인 취소가 가능하다(이력 3종: 승인/반려/취소).

**A-2 수정 요청**: 게시 카드에 대해 누구나 신청(USR-06, 현재 값 자동 표시 + 사유 필수) → 관리자 검토·처리(처리 큐 화면은 미구현, API 계약 선확보) → 처리 결과 알림.

**A-3 알림**: 발송 트리거는 전부 서버 책임 — 신청 접수·슬롯 승인·반려·승인 취소·수정 요청 처리·후기 등록. 소식(공지)은 알림을 발생시키지 않는다(0.10). 알림 클릭 시 카드 ID 접두어 파생 경로로 이동.

**A-4 개인화**: 스크랩·관심사·알림 읽음은 클라이언트 저장(0.2 키 표준) + 전 화면 실시간 동기화 → 연동 시 각각 scraps·me/interests·notifications API로 전환. 관심사는 랜딩 추천의 입력이 된다.

**A-5 집계**: 통계·대시보드·랜딩 카운터는 모두 카탈로그 단일 소스에서 파생(statsDerive)되어 총량이 항상 일치한다(0.9). 조회수는 인기 정렬·트렌딩 소스로만 쓰이며 서버 집계 전환 대상이다.
