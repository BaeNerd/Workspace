# AX Platform 화면별 기획 설명서 (v3)

작성 목적: 프론트엔드·백엔드·DB 개발 병행을 위한 공통 이해 문서.
각 화면의 정의 / 목적 / 기획 의도 / 지켜야 할 룰 / 화면 동작 / 화면 구조를 텍스트로 기술한다.
본 문서는 화면정의서(PPT 와이어프레임)의 서사 보완재이며, 코드 구현의 최종 근거는 저장소의 `STRUCTURE.md`와 소스이다.

- 저장소: `BaeNerd/Workspace` — `axplatform/` (프론트 `axplatform/frontend`, React + TypeScript + Vite)
- 대상: 사용자 화면 11종(USR-00~11, **USR-02 결번**) + 관리자 화면 9종(ADM-01~09). 랜딩(USR-00)은 외부 제작물을 내부 자산으로 편입 완료해 문서 대상에 포함한다.
- v2 변경: 코드 심볼을 현행 명칭(Asset/Category 체계)으로 갱신, 화면별 "화면 동작" 절 신설, 배경 설명을 처음 읽는 사람 기준으로 재서술.

## v3 변경 요약

v3은 랜딩 교체·공지 기능·전역 검수 수정·목업 정합 마감·개인화 실연동 이후의 상태를 문서에 반영한다. 핵심 내용은 다음과 같다.

- **랜딩 편입(USR-00 신설)**: 외부 제작 Next.js 랜딩을 Vite SPA로 포팅해 전면 교체하고 신 체계로 정합화했다. "LandingPage 교체 예정 / 문서 제외"라는 v2 전제를 걷어내고, 랜딩을 발견·개인화 허브로 정식 문서화한다. 교체와 함께 운영 상태 잔존 타입(`PlatformItemStatus` 계열)과 목업 `status` 필드가 **일괄 삭제**되었다(0.4 갱신).
- **신규 화면 4종**: USR-09 이용 가이드(`/guide`), USR-10 공지사항·업데이트 소식(`/notices`), USR-11 설정(`/settings`), ADM-09 공지 관리(`/admin/notices`).
- **개인화 축 신설(0.10)**: 스크랩(북마크)·알림·관심사 3축을 localStorage 단일 소스 + 공용 훅으로 전 화면 동기화한다. 개인화 패널·목록/랜딩 카드·상세 헤더·알림 벨이 모두 같은 소스를 공유한다.
- **공통 정책 보강**: 명칭 예외 목록에 localStorage 개인화 키 3종 추가(0.2), 조회수(views) 서버 집계 전환 방침·목업 SSOT 정합 원칙 명문화(0.9).
- **기존 화면 갱신**: 내비게이션(USR-08, 이용 가이드/알림 벨/설정 진입), 목록(USR-03, 스크랩 토글·필터), 상세(USR-04, 헤더 북마크·조회수).

# 0. 전 화면 공통 정책 (반드시 선행 숙지)

각 화면 설명에서 반복하지 않기 위해 공통 정책을 먼저 정리한다. 모든 화면은 이 정책을 전제로 한다.

## 0.1 플랫폼 포지셔닝

- AX Platform은 콜마그룹 29개 관계사 전 임직원이 SSO로 접근하는 **AX 자산 카탈로그**다. 그룹사 AX 확산 활동의 산출물 저장소 역할을 겸한다.
- IT 프로젝트 트래커가 아니다. MES/SRM/ERP 등 일반 IT 시스템 구축 과제, 플랫폼 인프라 구축, BI는 카탈로그 제외 대상이다.
- 콘텐츠 철학은 "질문 중심(question-driven)"이다. 각 카테고리는 사용자의 질문에 답하는 형태로 구성한다.
  - AI Model: "나는 어떤 AI Model을 써야 할까?"
  - 나만의 비서: "이런 프롬프트를 쓰니 편하더라"
  - Vibe Coding / AI 프로젝트: "내가 만든 것을 공유합니다"

## 0.2 7개 카테고리 체계

분류 기준은 "직원이 이 도구를 쓰려면 어디로 가야 하는가"(실행·운영 위치)다.

| 내부 id | 표시명 | 정의 | 비고 |
|---|---|---|---|
| n8n | n8n | 업무 자동화 워크플로우 플랫폼 | JSON 업로드로 다이어그램 자동 표시 |
| pa | Power Automate | Microsoft 자동화 도구 (클라우드 플로우 + RPA) | 흐름 구조는 스크린샷 + 텍스트로 전달 |
| assistant | 나만의 비서 | HK GPT를 프롬프트·역할로 커스터마이징해 공유하는 개인/팀 에이전트 | 공유 프롬프트가 핵심 콘텐츠 |
| ai-orchestration | AI Model | 업무 니즈에 맞는 AI 모델을 선택해 쓰는 사내 AI 게이트웨이(HK GPT) 모델 카탈로그 | **관리자 전용 등록** |
| ml | ML | 특정 플랫폼에 속하지 않는 독립 머신러닝 모델 | |

| etc | AI 프로젝트 | 팀에서 구축한 AI 시스템·서비스 사례를 블로그 형식으로 소개 | 일반 IT 시스템 구축 과제 제외 |

### 코드 명칭 규약 (개발자 필독)

- 사용자 노출 용어는 **"카테고리"**, 코드 심볼은 **category/asset 계열**로 통일되어 있다.
  - 타입: `CategoryId`(7종 유니온) · `Category`(카테고리 메타) · `AssetItem`(카탈로그 항목) · `AssetReview`(활용 후기)
  - 상수: `CATEGORIES`(7개 카테고리 메타 배열, 색·라벨·경로의 단일 소스) · `CATEGORY_ICON_PATH` · `ID_PREFIX` · `makeItemId`
  - 필드: `categoryId`(항목의 카테고리) · `companyScope`(승인 자격 판정용 내부 데이터)
  - 파일: `types/categoryTypes.ts` · `pages/AssetItemDetailPage.tsx` · `pages/admin/AdminCategories.tsx`
- **개별 자산의 사용자 노출 총칭은 "카드"로 표준화**한다 — 카탈로그 카드·관리 화면 헤더·안내·빈 상태·삭제 확인 등 렌더 문구에서 개별 자산 1건을 지칭할 때 "카드"를 쓴다(예: 카드 관리·"이 카드를 삭제하시겠습니까"). 코드 심볼(`AssetItem`)·내부 데이터·타입명은 불변이며 이 표준은 렌더 문자열에 한정한다. (舊 렌더 표기 "항목 관리"는 "카드 관리"로 교체됨 — ADM-03.)
- **명칭 예외(현행 유지, 변경 금지)**: 라우트 경로(`/admin/platforms`, `/n8n/:itemId` 등), API TODO 경로(`/api/v1/platform-items` 등 — 백엔드 계약 확정 시 정리), URL 쿼리 키 `?platform=`, 카테고리 값 문자열(`"n8n"`…`"etc"`), ID 접두어, 제품명 "AX Platform / AX 플랫폼", localStorage 키 `ax_recent_viewed`(최근 조회) · **`ax_scraps`(스크랩) · `ax_user_interests`(관심사) · `ax_notifications_read`(알림 읽음)**(개인화 3종 — 0.10 참조).
  - (v2에 예외로 적혀 있던 `PlatformItemStatus` 계열 @deprecated 타입은 랜딩 교체와 함께 **삭제 완료**되어 더 이상 "잔존 명칭 예외"가 아니다 — 0.4 참조.)

## 0.3 카드 ID 체계

- 형식: `{PREFIX}-{YYYY}-{NNN}` (예: N8N-2026-001). 접두어: N8N / PA / AST / AIO / ML / VIBE / ETC.
- 카테고리별·연도별 독립 순번. 결번 재사용 금지. 승인 전후 ID 불변.
- 발급 주체는 서버(백엔드). 등록 신청 INSERT 시 PostgreSQL 카테고리·연도별 시퀀스(또는 카운터 테이블)로 원자적 발급한다. 클라이언트 임의 생성 금지. 현재 프론트의 `makeItemId()`는 데모용이며 연동 시 서버 발급으로 교체한다.
- ID는 외부 노출 공식 식별자다. 상세 URL 경로에 그대로 사용한다 (`/n8n/N8N-2026-001`).

## 0.4 운영 상태를 두지 않는다 (핵심 설계 결정)

- 이 플랫폼에는 게시 후 "운영 상태"(사용 가능·점검 중 같은 표시) 개념이 **없다**. 등록 입력·상세 뱃지·목록 필터·URL 파라미터 어디에도 두지 않는다.
- 이유: 카탈로그의 항목은 "지금 돌아가는 서비스"가 아니라 "재사용 가능한 자산·사례"다. 상태 표시를 두면 등록자에게 상시 갱신 부담이 생기고, 갱신되지 않은 상태값은 오히려 오정보가 된다. 실제 이용 가능 여부는 담당자 문의로 확인하는 것이 정확하다.
- 유일한 예외: AI Model(ai-orchestration)의 가용 여부 `agentAvailability`("사용 가능"/"사용 불가"). AI Model는 관리자가 운영하는 사내 게이트웨이의 모델 목록이라 관리 주체가 명확하고, "지금 쓸 수 있는가"가 사용자 선택에 직결되기 때문에 이 축만 유지한다.
- **승인 수명주기와 혼동 금지**: 항목에는 승인 수명주기(승인 대기 → 게시됨 / 반려 / 중지)가 별도로 존재하며 이는 유지된다. "상태"라는 단어가 나오면 반드시 어느 쪽인지 구분한다.
- DB 설계 시사점: 항목 테이블에 운영 상태 컬럼을 만들지 않는다. 승인 수명주기는 승인 슬롯 데이터로 관리한다.
- **코드 잔존물 정리 완료(v3)**: v2 시점에는 프론트에 `PlatformItemStatus` 등 @deprecated 타입과 목업의 `status` 필드가 "교체 예정 LandingPage가 참조 중"이라는 이유로 임시 존치돼 있었다. 랜딩이 신 랜딩으로 교체(0.4 예외의 유일한 잔존 참조 제거)되며 `PlatformItemStatus`·`STATUS_ORDER`·`STATUS_COLOR`·`STATUS_QUERY_KEY`·`LEGACY_STATUS_MAP`·`normalizeStatus`·`countAvailable` 및 `AssetItem.status` 필드가 **일괄 삭제**되었다(전 목업의 `status` 리터럴 제거 포함, 전수 grep 코드 참조 0, `tsc -b`가 미참조 보증). `agentAvailability`(별개 축)와 `workflowDef.status`(`Stable`/`Active`/`Error`, 워크플로우 시각화 전용)는 상태 폐기와 무관하므로 유지한다. 신규 코드에서 운영 상태 개념 참조 금지.

## 0.5 항목 URL·관계사 정책

- 항목 단위 실행/접속 URL을 두지 않는다. 예외는 AI Model의 "모델 접속 URL"(`specificUrl`) 하나뿐이다.
  - 이유: 카테고리마다 "실행 주소"의 성립 여부가 다르다. 예컨대 Power Automate 플로우는 항목별 서비스 URL 개념이 없고(트리거 대상 리소스 주소만 존재), 나만의 비서·ML도 접근 경로가 제각각이다. 성립하는 유형에만 URL을 두면 화면 구조가 갈라지므로, 전 유형 공통으로 "담당자 문의" 방식으로 통일했다. AI Model만 사내 게이트웨이(HK GPT)라는 단일 진입점이 실재하므로 예외.
- 카테고리(플랫폼) 단위 외부 환경 링크(n8n 서버, HK GPT)는 Navbar "플랫폼 바로가기"로 별도 유지된다. 항목 URL 부재와 별개다.
- 항목에 소속/대상 관계사를 지정·표시하지 않는다. 전 항목 전사 공용으로 취급한다.
  - 이유: 자산 공유 플랫폼에서 관계사 딱지는 "우리 회사 것 아님"이라는 심리적 장벽을 만든다. "어디서 쓰는지"는 담당자 소속 부서 + 업무 도메인으로 충분히 표현된다.
  - 단, `company`/`companyScope` 필드는 승인 슬롯 자격 판정용 내부 데이터로 존치한다(화면 노출 없음).
  - **적용 범위 한정 (과잉 적용 금지 — 확정)**: 이 "관계사 표시 폐기"가 **금지하는 것은 단 하나** — **사용자 카탈로그 화면(랜딩·목록·상세·등록·수정 요청)에서 특정 항목에 관계사를 귀속시키는 표시**(예: 항목 카드/상세의 "○○사 자산" 딱지, "N개 그룹사 참여" 문구)다. 그 외에는 관계사 명칭·소속의 등장을 **전부 허용**한다:
    - **그룹 브랜딩 요소** — 랜딩의 참여 관계사 로고 마퀴(`PartnerMarquee`) 등. 특정 항목 귀속이 아닌 플랫폼 정체성 표현.
    - **본인 소속 안내** — Navbar 아바타 드롭다운의 로그인 사용자 소속 관계사 표시명(USR-08). "내가 누구 소속인가"는 항목 귀속과 무관.
    - **승인 주체 안내** — 승인 이력·슬롯 라벨의 "관계사 관리자 승인" 등 프로세스 설명.
    - **공지 본문** — 공지·최신소식 본문 텍스트에 관계사명이 등장하는 것(작성자 자유 서술).
    - **관리자 화면 전역** — 검토 큐·카드 관리·통계·조직 관리 등에서 "등록 관계사" 배지·범위 선택·집계 축. 관리자는 관계사 경계를 다뤄야 하는 주체이므로 표시가 오히려 필수다.
  - 요컨대 이 정책을 "관계사라는 단어가 화면에 나오면 안 된다"로 확대 해석하지 않는다 — 대상은 오직 **사용자 화면의 항목 귀속 딱지**다.

## 0.6 권한 체계 (2-tier)

- 역할은 User / Admin 2단계만 둔다. `isAdmin = role === "admin"`.
  - 이유: 역할 종류를 늘리면(예: 시스템관리자·콘텐츠관리자 분리) 권한 매트릭스가 기하급수로 복잡해진다. 대신 Admin 안에서 **범위(scope)** 로 구분한다.
- Admin의 범위: `adminScope = "global"`(전사관리자, 전체 권한) / `"company"`(관계사관리자, `managedCompanies: string[]`에 담긴 관계사만 관리). 미지정 레거시 계정은 global로 간주.
- 관계사와 관리자는 N:M 관계다(한 관리자가 여러 관계사 담당 가능, 한 관계사에 여러 담당자 가능).
- 불변 규칙: **전사관리자는 최소 1명 유지**한다. 마지막 global 권한 회수는 UI와 서버 양쪽에서 차단한다(관리 불능 상태 방지).
- AI Model 등록·수정은 관리자 전용. 프론트 폼에서 `isAdmin` 가드하며, 백엔드 연동 시 서버측 검증 필수(프론트 가드만으로는 불충분).
- `canManageItem`은 항상 **원본 항목** 기준으로 판정한다. 편집 중인 값 기준으로 판정하면 값을 고쳐 권한을 우회할 수 있기 때문이다.

## 0.7 승인 워크플로우 (병렬 2-슬롯)

- 게시에는 두 개의 승인이 모두 필요하다: **관계사 관리자 승인** + **전사 관리자 승인**. 각각을 "슬롯"이라 부른다.
- 두 슬롯은 **순서 없이 병렬**로 진행된다. 어느 쪽이 먼저 승인해도 되고, 두 슬롯이 모두 채워지는 순간 게시된다.
  - 이유: 순서를 강제하면(앞 승인이 끝나야 뒤 승인 시작) 앞 단계가 병목이 되어 전체 처리 시간이 앞 사람의 응답 속도에 묶인다. 병렬 구조는 두 검토자가 서로를 기다리지 않게 해 평균 게시 소요를 줄인다.
- 반려는 어느 슬롯에서든 가능하며 **사유 필수**. 반려 사유는 신청자에게 원문 그대로 전달된다.
- 수명주기: 신청 접수 → 승인 대기(슬롯 0~1개 완료, 1개 완료 시 "부분 승인") → 게시됨(2/2) / 반려 / 중지.
- 코드 참조: `ApprovalSlotKey`("company"|"global") · `ApprovalSlots` · `deriveStage()` (`types/categoryTypes.ts`).
- DB 시사점: 승인 이력 테이블(누가, 어느 슬롯, 언제, 승인/반려, 사유)과 항목의 슬롯 현황이 필요하다. 슬롯 갱신·이력 기록·게시 전환 판정(2/2)은 하나의 트랜잭션으로 묶는다.

## 0.8 예상 절감 시간 표준

- 자동화 카테고리(n8n, pa)의 "예상 효과"는 `값 + 주기` 구조로 입력받아 표준 문자열로 저장한다(`expectedTimeSaved`, 입력 컴포넌트 `TimeSavedInput`).
- 원본 자유 텍스트 보존 원칙. 집계 시 주기별 배수로 환산하되 용도별 기준이 다르다: 관리자 통계는 **연간 환산**(운영 성과 리포트 관점), 랜딩 노출은 **주간 환산**(지금 이 순간의 실효 가치 관점). 파싱 불가 값은 부풀리지 않고 "추정 불가"로 별도 카운트한다.

## 0.9 API·데이터 공통

- 백엔드 표준 스택: FastAPI + PostgreSQL. Phase 2에서 pgvector 기반 RAG/LLM 검색 예정.
- **통계 총량 = 카탈로그 총량 일치 원칙**: 통계·대시보드·랜딩의 수치는 자산 SSOT(카탈로그)에서 파생하며, 전 화면 총 등록물·월별 추이 합·관계사 합·도메인 합이 카탈로그 총량과 항상 일치한다. 합성 집계 더미(관계사 차원 임의 테이블)를 두지 않는다.
- 프론트 전 페이지는 목업 데이터로 동작하며 `// TODO: 실제 연동 시 ...` 주석이 교체 지점이다. `lib/api.ts`에 `api.get/post/put/delete` 래퍼 준비됨.
- 존재하지 않는(만들면 안 되는) 엔드포인트: 운영 상태 변경 API. 0.4에 따라 개념 자체가 없다.
- 승인/수정 API body에는 `company`·`companyScope`를 포함하지 않는다(서버 내부 데이터). 항목 페이로드에 `images: string[]` 포함.
- 이미지 저장: 현 데모는 data URL을 목업에 인라인. 연동 시 별도 업로드 스토리지(오브젝트 스토리지 등) + URL 참조 방식 필요. 항목당 최대 10장.
- **조회수(views) 서버 집계 전환 방침**: 항목에는 `AssetItem.views?: number` 필드가 있고, 카드·상세 헤더에 좋아요와 병기되며 랜딩 "실시간 인기"·목록 인기 정렬의 소스다. 현재는 목업 상수이며, 연동 시 **서버 집계**로 전환한다 — 상세 조회 이벤트를 서버가 카운트(중복 방지·기간 가중 트렌딩 스코어는 백엔드 책임)하고 목록·랜딩은 집계값을 읽기만 한다. 클라이언트에서 조회수를 증분·저장하지 않는다. 랜딩 "실시간 인기"의 `views` 정렬은 연동 시 기간 가중 트렌딩 API로 교체(코드 TODO 주석 존재). 조회수 축은 관리자 통계에 추가하지 않는다(입력 없는 축을 만들지 않는 원칙 — ADM-04).
- **목업 정합 원칙(SSOT)**: 데모 목업 데이터는 **상세 페이지(카탈로그 SSOT)를 단일 정본**으로 삼는다. 여러 화면이 같은 카드 ID를 참조할 때 제목·요약·담당자 등 표시 문자열은 SSOT와 일치해야 하며, **동일 ID에 상이한 제목을 부여하는 것을 금지**한다(대기 큐의 미게시 항목처럼 SSOT에 없는 데모 항목은 카테고리·연도 다음 순번의 신규 ID를 발급해 충돌을 피한다). 감사 로그 등 이력 레코드는 원본 보존 원칙에 따라 소급 정정하지 않는다.
- 좋아요/게시판 백엔드 스키마(백로그 확정안): 항목 좋아요 · 게시글 · 게시글 좋아요 3테이블. 좋아요는 PUT/DELETE 멱등 설계, 프론트는 낙관적 갱신 + 실패 시 롤백. (테이블 명명은 백엔드 착수 시 asset 계열로 확정 — 부록 B 참조)

## 0.10 개인화 체계 (스크랩·알림·관심사)

개인 상태(스크랩·관심사·알림 읽음)는 **localStorage 3종**을 단일 소스로 두고, 공용 훅(`hooks/`)이 `useSyncExternalStore`로 같은 탭 내 모든 소비자(상세 헤더·목록/랜딩 카드·개인화 패널·알림 벨)를 즉시 동기화한다. 다른 탭 변경은 `window "storage"` 이벤트로 반영한다. 목업(알림)과 localStorage 상태를 병합해 파생값을 만든다. **DEMO 전용** — 백엔드 연동 지점은 각 훅·발송부의 TODO 주석에 명시돼 있다.

설계 의도: 개인화는 "내 활동 맥락"을 화면 간에 끊김 없이 이어주는 층이다. 세 축(스크랩·알림·관심사)을 각각의 화면에 흩어 두지 않고 **단일 localStorage 키 + 단일 훅**으로 묶어, 어느 화면에서 상태를 바꿔도 나머지 화면이 즉시 같은 값을 보게 했다. 백엔드 연동 시 이 훅들이 그대로 API 호출 지점이 된다.

### 개인화 localStorage 키

| 키 | 형태 | 소유 훅 | 용도 |
|----|------|---------|------|
| `ax_scraps` | `string[]` (itemId) | `hooks/useScraps` | 스크랩(북마크) 항목 목록 |
| `ax_user_interests` | `{ categories: CategoryId[]; domains: BusinessDomain[] }` | `hooks/useInterests` | 관심 카테고리·업무 도메인 |
| `ax_notifications_read` | `string[]` (알림 id) | `hooks/useNotifications` | 읽음 처리한 알림 id 집합 |

### 스크랩(북마크)

- localStorage **`ax_scraps`**(itemId 문자열 배열) 단일 소스. `useScraps()` → `{ scraps, count, isScrapped(id), toggle(id) }`, 모듈 레벨 `toggleScrap`·`isScrapped`도 export(컴포넌트 밖 호출용).
- 토글 지점 3곳: **상세 헤더**(좋아요 옆 "스크랩" 버튼) · **목록 카드**(조회수·좋아요 옆 북마크, 카드 클릭과 분리하려 `stopPropagation`) · **랜딩 카드**(`ItemCard` 우상단 북마크).
- 개인화 패널 "내가 스크랩한 카드 N개" 행이 `count`를 표시하고, 클릭 시 **`/projects?scrap=1`**로 이동한다 — 별도 스크랩 페이지를 신설하지 않고 목록을 재사용한다(단순한 쪽 선택, 코드 주석에 명시).
- **백엔드 후보**: `scraps` 테이블(`user_id`·`item_id`) + 멱등 **PUT/DELETE `/api/v1/scraps/:itemId`**.

### 알림

- **kind 7종**(`NotificationKind`, `types/notificationTypes.ts`에서 열거를 그대로 옮김):
  - `신청접수` — 등록 신청이 접수됨
  - `관계사승인` — 관계사(company) 슬롯 승인 (1/2), 다른 슬롯 대기 문구로 병렬성 노출
  - `전사승인` — 전사(global) 슬롯 승인 (1/2) 또는 두 슬롯 완료 게시(2/2) — title/body 문구로 구분
  - `반려` — 승인 반려 (사유 `body` 포함)
  - `후기등록` — 내 항목에 활용 후기가 등록됨
  - `게시판글` — 내 항목의 "업데이트·논의"에 새 글이 등록됨
  - `수정요청처리` — 내 수정 요청이 처리(반영/보류)됨
- **공지(Notice)는 알림을 발생시키지 않는다(확정 결정)**. 알림은 오직 "내 활동"에 대한 개인 통지만 다룬다 — 공지사항·업데이트 소식은 랜딩 최신소식과 `/notices`에서 열람하는 브로드캐스트 채널이지 개인 알림이 아니다. 두 채널을 섞으면 공지 한 건이 전원에게 알림 폭주를 일으키므로 축을 분리한다.
- 표시: `NotificationBell`(공용 벨)이 미읽음 뱃지 + 드롭다운(최근 5건 · 전체 읽음 · 항목 이동)을 렌더한다. 읽음 상태는 **`ax_notifications_read`**(읽은 id 배열)와 목업 시드의 `read`를 병합해 파생(`read = 시드 read || 읽음 집합 포함`). 개인화 패널 "알림 현황" 블록도 동일 소스(`useNotifications`)로 최근 3건·미읽음을 강조한다.
- **발송 트리거는 서버 책임**: 실제 알림 생성은 승인/반려/수정 처리 시점에 서버가 수행한다. 프론트에는 발송 지점을 표시하는 **TODO 주석만** 두었고 로직은 넣지 않았다 — `AdminReview.approveSlot`(kind `관계사승인`/`전사승인`, 게시 시 2/2 문구) · `AdminReview.handleReject`(kind `반려`) · `EditRequestPage.handleSubmit`(kind `수정요청처리`).
- 항목 이동은 `detailPathForItemId(itemId)`가 접두어만으로 상세 경로를 파생하므로, 벨·알림이 목업 배열을 import하지 않고도 이동할 수 있다.
- **백엔드 후보**: **GET/PATCH `/api/v1/notifications`**(목록 조회·읽음 처리).

### 관심사

- localStorage **`ax_user_interests`**(`{ categories: CategoryId[]; domains: BusinessDomain[] }`) 단일 소스. `useInterests()` → `{ interests, hasInterests, save(next) }`. `save`는 기록 후 구독자에 통지해 패널 추천을 즉시 갱신한다.
- 설정 화면(USR-11)에서 관심 카테고리(7종)·관심 도메인(6종)을 다중 선택해 저장한다.
- **추천 매칭 규칙**: 개인화 패널 "나에게 추천하는 카드"는 관심 카테고리 **또는** 관심 도메인과 일치하는 항목을 `views` → `likes` 순으로 정렬해 상위 `RECOMMEND_N=12`개를 보인다(`LandingPage.recommendItems`). 관심사 미설정 시 추천 대신 "관심사를 설정하면 맞춤 추천을 받아요" 문구 + `/settings` 유도를 렌더한다.
- **백엔드 후보**: **PUT `/api/v1/me/interests`**(저장) + 추천 API(`GET /api/v1/me/recommendations`).

# PART 1. 사용자 화면

## USR-00 랜딩 (LandingPage, /)

**정의·역할**: 비로그인·로그인 공통의 최초 진입 화면(공개 페이지, 인증 불필요). 플랫폼의 얼굴이자 발견·개인화 허브다. 외부 제작 Next.js 랜딩(`_incoming-landing/`)을 Vite SPA로 **포팅해 전면 교체**하고 신 체계로 정합화한 **내부 자산**이다(더 이상 "외부 제작물 교체 예정"이 아니다). 외부 CDN 이미지·라이브러리 의존 없이 로컬 에셋·로컬 폰트·CSS 애니메이션만 사용하는 자기완결 구현이다.

**목적**: 처음 온 사람에게 "여기가 무엇을 모으는 곳인가"를 한 화면에서 체감시키고, 카테고리·인기 항목·업무 도메인·최신소식으로의 진입로를 열어 탐색을 시작하게 한다. 로그인 사용자에게는 개인화 패널로 "내 스크랩·추천·알림"을 즉시 보여 재방문 가치를 만든다.

**기획 의도**: 랜딩은 카탈로그의 **쇼윈도**다. 목록(USR-03)이 "찾으러 온 사람"의 도구라면, 랜딩은 "무엇이 있는지 아직 모르는 사람"에게 폭을 보여주는 면이다. 그래서 배너 슬라이더·회전 헤드라인·카테고리 타일·현황 카운터 같은 **발견 유도 장치**를 앞세운다. 동시에 신 정책과의 정합을 최우선으로 지켰다 — 원본에 있던 관계사 로고 마퀴·그룹사명 표시·운영 상태·항목 실행 URL을 모두 걷어내고(0.4·0.5), 목업 항목은 카탈로그 SSOT와 ID·제목을 일치시키고(0.9), 최신소식은 정적 배열이 아니라 공지 단일 소스(`noticeMockData`)를 참조하게 했다. 애니메이션은 외부 라이브러리를 들이지 않고 CSS 키프레임 + `rAF`/`IntersectionObserver`로 원본 시그니처를 재현해 자기완결성을 지켰다.

**화면 동작**
- **[1] 프로모션 + 개인화**: 상단에 카테고리 배너 슬라이더(5초 자동 전환 + prev/next)와 개인화 패널이 나란히 놓인다. 개인화 패널은 로그인 사용자에게 인사·개인화 지표·퀵액션을 보인다.
  - "내가 스크랩한 카드 N개" 행 → 클릭 시 `/projects?scrap=1`(스크랩 필터 목록)로 이동. 카운트는 `useScraps().count` 실시간 반영.
  - "나에게 추천하는 카드" → 관심사 매칭 추천(관심 카테고리 또는 도메인 일치 항목을 `views`→`likes` 순 상위 12). 관심사 미설정 시 "관심사를 설정하면 맞춤 추천을 받아요" + `/settings` 유도.
  - "알림 현황" 블록 → 최근 3건·미읽음 강조, 알림 벨과 동일 소스(`useNotifications`).
  - 퀵액션: 내 등록 현황(`/my-status`) · **설정(`/settings`)** · 항목 등록(`/projects/new`) · 로그아웃.
- **[2] 아이콘 히어로**: 회전 헤드라인 + 검색 폼(제출 시 `/projects?q=`) + 카테고리 7타일(클릭 시 `/projects?platform=<id>`).
- **[3] 플랫폼 현황**: 총 항목 카운터(스크롤 진입 시 rAF 카운트업) + 카테고리별 막대그래프(IntersectionObserver 진입 시 채움). 수치는 카탈로그 SSOT 실계수에서 산출(하드코딩 아님, TODO 주석).
- **[4] 인기 항목**: 카테고리 필터 + 항목 카드. 카드 우상단 북마크로 **스크랩 토글**, 조회수(views)·좋아요 병기.
- **[5] 최신소식 + 실시간 인기**: 공지/업데이트 탭은 **`mocks/noticeMockData` 단일 소스**를 참조(visible=true·pinned 우선·최신순, 탭별 최대 5건). "더보기" 및 각 행 클릭 → `/notices?kind=`. "실시간 인기"는 `views` 기준 정렬(연동 시 트렌딩 API로 교체 TODO).
- **[6] 업무별 항목**: 업무 도메인(`BUSINESS_DOMAINS` 6종) 필터 + 항목 카드(클릭 시 상세, 도메인 칩 → `/projects?domain=`).
- **[7] 시작 도우미 CTA**: 4-박스 진입(둘러보기·AI Model·**이용 가이드(`/guide`)**·문의 채널). 문의 채널은 Teams 새 탭 이동(공유 모드에서는 안내 배너로 대체).

**지켜야 할 룰**
- 최신소식은 반드시 공지 단일 소스(`noticeMockData`)를 참조한다. 랜딩 전용 정적 뉴스 배열을 다시 만들지 않는다(중복 정의 금지).
- 항목(자산) 단위 관계사(그룹사) 표시·"N개 그룹사 참여" 문구를 두지 않는다(0.5). 운영 상태 표시·항목 실행 URL을 두지 않는다(0.4·0.5, AI Model 예외 제외).
- **참여 관계사 로고 마퀴(`PartnerMarquee`)는 그룹 브랜딩 요소로 관계사 표시 폐기(0.5) 대상이 아니다** — 현재 원본 소실(`_incoming-landing` 저장소 부재)로 원본 컴포넌트·로고 에셋 재확보가 필요해 **별도 담당자가 복원 예정**(임의 창작 금지).
- 목업 항목(`LANDING_ITEMS`)의 ID·제목은 카탈로그 SSOT(`ProjectListPage`)와 일치시킨다(0.9). 링크는 실제 라우트(`/projects`·`?platform=`·`?domain=`·상세 경로)로 연결한다.
- 개인화 패널 지표는 정적 placeholder가 아니라 실연동값(스크랩 카운트·관심사 매칭 추천·알림 현황)을 쓴다.
- 자기완결: 외부 CDN 이미지·외부 애니메이션 라이브러리를 도입하지 않는다. 로컬 폰트(`SB Aggro`·`SCoreDream`, `public/fonts/`)·로컬 이미지(`public/banner|icons|cta/`)·CSS/rAF만 사용한다.
- 서브컴포넌트·스타일 객체는 모듈 레벨 정의(코딩 규약).

**화면 구조**
```
랜딩 (/)
├─ [1] 프로모션 + 개인화 (배너 슬라이더 · 개인화 패널: 스크랩/추천/알림/퀵액션)
├─ [2] 아이콘 히어로 (회전 헤드라인 · 검색 · 카테고리 7타일)
├─ [3] 플랫폼 현황 (총 항목 카운터 · 카테고리별 막대)
├─ [4] 인기 항목 (카테고리 필터 · 카드[스크랩·조회수·좋아요])
├─ [5] 최신소식 + 실시간 인기 (공지/업데이트 탭[noticeMockData] · views 랭킹)
├─ [6] 업무별 항목 (도메인 필터 · 카드)
└─ [7] 시작 도우미 CTA (둘러보기 · AI Model · 이용 가이드 · 문의)
```

**개발 연동 노트**: 최신소식은 `GET /api/v1/notices`(공개, visible만), 추천은 `GET /api/v1/me/recommendations`, 스크랩 카운트·알림 현황은 개인화 API(0.10)로 채운다. 현황 카운터·인기 정렬의 `views`는 서버 집계로 전환(0.9). 공유 빌드(`build:share`, `VITE_SHARE_MODE`)는 이 랜딩만 담은 단일 HTML을 산출하는 별도 모드로 유지된다(STRUCTURE.md의 공유 빌드 체계 참조).

## USR-01 로그인 (LoginPage, /login)

**정의·역할**: 플랫폼 진입 관문. 데모 단계에서는 역할(일반 사용자/관리자) 선택형 목업 로그인이며, 운영 전환 시 그룹 SSO로 대체된다.

**목적**: 전 임직원이 별도 가입 절차 없이 사내 계정으로 즉시 진입하게 한다. 데모 기간에는 권한별 화면 차이를 시연할 수 있게 한다.

**기획 의도**: 카탈로그의 확산 목표상 진입 장벽은 0이어야 한다. 로그인은 신원 확인일 뿐 권한 부여 절차가 아니며, 권한(adminScope, managedCompanies)은 서버가 계정에 대해 내려주는 값이다. 화면에 안내 외의 기능을 두지 않는다.

**화면 동작**
- 사용자가 역할 카드를 선택하고 입장 버튼을 누르면 → 세션이 생성되고(데모: sessionStorage) → 로그인 전 가려던 화면이 있으면 그 화면으로, 없으면 랜딩으로 이동한다.
- 미인증 상태로 보호된 화면(등록·내 현황·관리자 등)에 접근하면 → `/login?redirect=<원래경로>`로 보내지고, 로그인 성공 시 원래 경로로 자동 복귀한다(`ProtectedRoute` 처리).
- 관리자로 로그인하면 이후 Navbar에 관리자 진입 아이콘이 나타나고 AI Model 등록 카드가 노출되는 등 화면 전반이 권한에 따라 달라진다. 운영 전환 시: 로그인 버튼 → SSO 인증 → 서버가 프로필·권한 반환 → 동일 복귀 흐름.

**지켜야 할 룰**
- 새로고침 후에도 세션 유지(데모: sessionStorage). 운영 전환 시 `GET /api/v1/auth/me`로 세션 확인하며, 응답에 `company`, `isGroupViewer`, `adminScope`, `managedCompanies`가 반드시 포함되어야 한다.
- "사내 전용 플랫폼" 고지를 유지한다.

**화면 구조**
```
로그인 화면
├─ 브랜드 영역 (서비스명 + 한 줄 소개)
├─ 로그인 폼 (데모: 역할 선택 → 입장 / 운영: SSO 버튼)
└─ 하단 고지 (사내 전용 안내)
```

**개발 연동 노트**: 백엔드는 SSO 콜백 → 세션/토큰 발급 → `/auth/me` 프로필 반환 흐름을 설계한다. DB `users`에는 소속 관계사 코드, 역할, adminScope, managedCompanies(N:M 매핑 테이블 권장)가 필요하다.

## USR-02 — 폐지(2026-07), 콘텐츠는 USR-09 가이드로 흡수. 번호 결번 유지

**USR-02 소개(About, `/about`)는 2026-07 폐지되었다.** 이용 가이드(USR-09)와 "무엇을/왜/어떻게"의 역할이 중복되어, 핵심 섹션 **"왜 AX Platform인가요?"**(Problem→Solution 4조)를 USR-09 가이드 인트로로 이관하고 화면을 걷어냈다. **번호는 결번으로 유지**하며 재배번하지 않는다.

- **라우트**: `/about`는 화면을 마운트하지 않고 `<Navigate to="/guide" replace />`로 `/guide`에 리다이렉트한다(구 링크·북마크 안전을 위한 1줄만 잔존).
- **진입점 정리**: 상단 메뉴는 이미 "이용 가이드"였다. 폐지와 함께 **푸터 "서비스 소개" 링크**(USR-08)와 **가이드 FAQ 하단의 About 진입 링크**(USR-09)를 제거했다(교체 아님).
- **콘텐츠 처리**: "왜 AX Platform" 섹션은 문구·구성 그대로 이관하되 **섹션 부제만 확정 변경**했다(아래 USR-09 참조). 소개 FAQ 4문항 중 고유 문항 **"문의는 어디로 하나요?"**만 가이드 FAQ로 편입하고, 나머지(누가 쓰나·평가 반영·등록 대상)는 가이드와 중복이라 폐기했다. 그 밖의 섹션(무엇을 다루나·질문에서 출발·어떻게 이용하나·CTA 배너)은 가이드·랜딩·공통 정책(0.1)과 중복되어 폐기했다.

## USR-03 카탈로그 목록 (ProjectListPage, /projects)

**정의·역할**: 7개 카테고리의 게시 항목을 단일 그리드에서 탐색하는 통합 검색 진입점. 플랫폼의 메인 발견(discovery) 화면. 개인화 패널의 "내가 스크랩한 카드" 진입 대상(`?scrap=1`)을 겸한다 — 전용 스크랩 페이지 대신 이 목록을 재사용한다.

**목적**: "우리 그룹에 어떤 자동화·AI 자산이 있는가"를 필터 두세 번으로 도달 가능하게 한다.

**기획 의도**: 카테고리별로 별도 목록 화면을 두는 대신 **단일 검색 진입점**(AWS Marketplace식 발견 경험)을 택했다. 사용자는 "n8n을 보러" 오는 것이 아니라 "내 업무에 쓸 것"을 찾으러 오기 때문에, 유형을 넘나드는 한 화면 탐색이 목적에 맞다. 카드는 **"카드는 미리보기, 상세는 상세 페이지"** 원칙으로 전 유형 동일한 정보 구조·고정 높이를 갖는다 — 유형마다 정보량이 다르면 그리드가 들쭉날쭉해지고 비교가 어려워지기 때문이다. 필터 축은 카테고리·도메인·검색 3개로 최소화했다 — 필터가 적을수록 탐색이 빠르고, 관계사별 구분은 자산 공유에 장벽이 되므로 사용자 화면에 두지 않는다(0.5, 관계사별 현황은 관리자 통계의 몫). **스크랩 필터를 별도 페이지가 아니라 이 목록의 토글 칩으로 얹은 이유**도 같다 — 스크랩은 "내가 표시해 둔 부분집합"일 뿐 다른 탐색 문법이 아니므로, 화면을 하나 더 만드는 대신 기존 그리드를 그대로 쓰는 것이 단순하다.

**화면 동작**
- 카테고리 칩(7종)을 클릭하면 → 즉시 해당 카테고리로 필터링되고 URL에 `?platform=<id>`가 반영된다(공유 가능 링크). 도메인 드롭다운·검색어 입력도 동일하게 즉시 반영.
- 초기화 버튼 → 전 필터 해제. 다른 화면에서 필터 링크로 진입한 경우에도 동작.
- 정렬(최신/인기/이름) 변경 → 목록 즉시 재정렬.
- 카드 클릭 → 해당 항목 상세(`/{카테고리값}/{항목ID}`, 예: `/n8n/N8N-2026-001`)로 이동. 카드의 하트 아이콘 클릭 → 좋아요 토글(카드에서 즉시 반영).
- **스크랩 토글**: 카드의 북마크 아이콘(조회수·좋아요 옆) 클릭 → 스크랩 토글. 카드 클릭(상세 이동)과 분리하기 위해 `stopPropagation`으로 전파를 막는다(상세 헤더·랜딩 카드와 동일 소스 `ax_scraps`).
- **스크랩 필터**: 2행 필터바의 "스크랩 N" 토글 칩으로 스크랩한 항목만 보기. `?scrap=1`로 진입하면 초기값이 켜진다(이후 상태는 로컬 유지). 스크랩 0건일 때 "아직 스크랩한 카드가 없습니다 — 카드나 상세에서 북마크를 눌러 스크랩해 보세요" 빈 상태 안내.
- 결과가 24개를 넘으면 "더 보기" 버튼으로 24개씩 증분 로드. 결과 0건이면 빈 결과 안내 + 필터 초기화 유도.
- URL에 `?status=` 같은 정의되지 않은 파라미터가 있어도 오류 없이 무시된다.

**지켜야 할 룰**
- 필터 축: 카테고리(7종) + 업무 도메인 + 검색어. 정렬: 최신/인기/이름. 운영 상태·관계사 필터를 두지 않는다. (스크랩 토글은 개인화 부분집합 필터로, 분류 축이 아니라 "내 표시" 필터다.)
- URL 파라미터는 `q`·`platform`·`domain`만 해석한다. `scrap`은 진입 시 초기값으로만 읽고 이후 URL에 유지하지 않는다.
- 카드 정보 구조 통일: 카테고리 뱃지 + 도메인 뱃지 + 제목 + 한 줄 요약 + 태그(최대 3) + 부서 + 조회수 + 좋아요 + 스크랩 토글. 카드 높이 고정.
- 카드 메타에 **카드 ID**를 노출한다 — 공용 컴포넌트 `CardIdTag`(0.3 형식, 선택 가능 텍스트)로 **등록 부서 왼쪽에 고정**한다. 지점별 개별 스타일 금지(단일 컴포넌트).
- 카테고리 뱃지 색·라벨은 `CATEGORIES` 단일 소스에서 파생한다(개별 하드코딩 금지).
- 비노출 관계사(visible=false) 항목은 해당 관계사 소속이 아닌 일반 사용자에게 숨긴다(그룹 뷰어 예외). 이는 접근 게이팅이며 사용자에게 필터로 노출하지 않는다.
- AI Model 카드 제목은 모델명 단독 표기(제공사 병기 없음 — 제공사는 상세에서 확인).

**화면 구조**
```
카탈로그 목록
├─ 상단 필터 바 (2행, sticky)
│  ├─ 1행: 카테고리 칩(7종) + 업무 도메인
│  └─ 2행: 태그/검색 + 스크랩 N 토글 + 초기화
├─ 정렬 컨트롤 (최신/인기/이름)
├─ 카드 그리드 (통일 카드 × N, 더 보기 24개 단위, 카드에 스크랩 북마크)
└─ 빈 결과 안내 (스크랩 0건 안내 포함)
```

**개발 연동 노트**: 목록 API가 필터·정렬·페이지네이션 파라미터를 받는다. 스크랩 필터는 서버 연동 시 `scraps` 조인 또는 별도 `?scrap=1` 파라미터로 처리(현재는 localStorage `ax_scraps` 기준 클라이언트 필터, 0.10). DB 인덱스는 카테고리·도메인·갱신일·좋아요·조회수 조회 패턴을 고려한다. 좋아요·조회수는 집계 컬럼 또는 카운트 캐시 전략 필요.

## USR-04 항목 상세 (AssetItemDetailPage, /{카테고리값}/{항목ID})

**정의·역할**: 게시 항목 1건의 전체 정보를 보여주는 화면. 카드에서 덜어낸 모든 정보의 종착지이자, 항목별 커뮤니티(후기·게시판)의 거점. 7개 카테고리 값 각각이 라우트 접두어가 된다(`/n8n/:itemId` ~ `/etc/:itemId`). 목업 데이터의 **SSOT**(단일 정본)로, 다른 화면의 동일 ID 항목 표시는 이 페이지를 기준으로 정합한다(0.9).

**목적**: "이걸 우리 팀에도 적용할 수 있을까"를 판단할 근거(구조, 효과, 담당자)를 제공하고, 담당자 연결과 후기 축적을 통해 재사용을 실제로 일으킨다.

**기획 의도**: 항목에 실행 URL이 없으므로(0.5) 상세 페이지의 실질적 행동 유도는 **담당자 문의**다. 따라서 담당자 정보가 명확한 위치를 가진다. 커뮤니티는 전체 공용 게시판이 아니라 **항목별 개별 게시판**이다 — 항목 맥락 안에서 Q&A가 이루어져야 지식이 그 자산에 귀속되어 다음 사람에게 쌓인다. 카테고리별 상세 구성이 다른 것은 질문 중심 콘셉트의 귀결이다: n8n은 구조(다이어그램), AI Model는 선택 판단(모델 사양), vibe·AI 프로젝트는 이야기(블로그형)가 각각 핵심 콘텐츠이기 때문이다.

**화면 동작**
- 진입 시 항목을 조회해 헤더·개요를 표시하고, 방문 기록을 로컬(`ax_recent_viewed`, 최대 10건)에 남긴다. 존재하지 않는 ID면 안내 + 목록 복귀 링크.
- 탭 클릭으로 개요/상세/담당자/업데이트·논의 전환. vibe·AI 프로젝트는 상세 탭이 아예 표시되지 않고 개요에 통합된다(`hasDetailTab=false`).
- 이미지가 있으면 개요 상단 캐러셀: 좌우 화살표로 넘기고 현재 n/전체가 표시된다. 이미지는 비율 유지(contain)·최대 높이 제한.
- 헤더에 **조회수(views)**가 좋아요와 병기된다(눈 아이콘 + 수치). 헤더의 하트 클릭 → 좋아요 토글(즉시 반영, 연동 후 낙관적 갱신+실패 롤백).
- **헤더 북마크(스크랩) 토글**: 좋아요 옆 "스크랩" 버튼 클릭 → 스크랩 토글(localStorage `ax_scraps`). 목록/랜딩 카드·개인화 패널 카운트와 실시간 동기화(0.10).
- 나만의 비서: 공유 프롬프트 영역의 복사 버튼 → 클립보드 복사 + 완료 피드백.
- n8n: 상세 탭에서 워크플로우 다이어그램(`WorkflowDiagram`)이 렌더링된다(등록 시 업로드한 JSON 기반).
- AI Model: 헤더에 가용 뱃지("사용 가능" 녹색/"사용 불가" 회색), `specificUrl`이 있으면 "모델 접속" 버튼 → 새 탭으로 HK GPT 이동.
- 개요 하단 후기 섹션: 별점+한 줄 후기를 작성·등록하면 목록에 즉시 추가. 게시판 탭: 태그(공지/Q&A/이슈제보/건의)를 골라 글 작성, 각 글에 좋아요 가능.
- 브레드크럼·카테고리 뱃지 클릭 → 해당 카테고리 필터가 걸린 목록으로 이동.

**지켜야 할 룰**
- 탭 구성: 개요 / 상세(카테고리별) / 담당자 / 업데이트·논의(게시판).
- 카테고리별 상세 내용:
  - n8n "상세 동작": 워크플로우 다이어그램 + 예상 효과 + 구성 난이도
  - Power Automate "플로우 정보": 예상 효과 (구조 전달은 이미지 캐러셀 + 상세 설명)
  - 나만의 비서 "비서 구성": 공유 프롬프트(복사 버튼) + 기반 모델
  - AI Model "모델 사양": 가용 뱃지 + 강점·활용 방법(우선 노출) + 세부 모델명 + 처리 가능한 글 분량 + 비용 등급 + 모델 접속 버튼
  - ML "모델 정보": 모델 유형 + 학습 데이터 개요 + 개발 도구
- 헤더에 조회수·좋아요·스크랩 토글을 병기한다. 운영 상태 뱃지·실행 버튼을 두지 않는다(예외: AI Model 가용 뱃지·모델 접속 버튼). 관계사(항목 귀속 딱지)를 표시하지 않는다(0.5).
- 헤더 메타 줄에 **카드 ID**를 공용 `CardIdTag`로 **등록 부서 왼쪽에 고정** 표시한다(0.3).
- 헤더에 **"수정 요청" 진입 버튼**을 둔다 → `/edit-request/:id`(USR-06). 게시 항목의 정보 정정을 검토 절차로 잇는 인바운드 진입점.
- 후기(`AssetReview`)는 개요 탭 내부 섹션에서 등록한다(별도 탭 아님).
- AI Model 제목은 모델명 단독. 제공사는 상세 설명·세부 모델명 등 본문에서 확인.

**화면 구조**
```
항목 상세
├─ 헤더 (카테고리 뱃지 · 제목 · 카드 ID · 조회수 · 좋아요 · 스크랩 · [AI Model: 가용 뱃지/모델 접속])
├─ 탭 바 (개요 / [상세] / 담당자 / 업데이트·논의)
├─ 개요 탭
│  ├─ 이미지 캐러셀 (있을 때)
│  ├─ 한 줄 요약 + 상세 설명 (트리거·동작 서술 포함)
│  ├─ 업무 도메인 · 태그
│  └─ 활용 후기 섹션 (목록 + 등록)
├─ 상세 탭 (카테고리별 구성 — 위 룰 참조)
├─ 담당자 탭 (부서 · 이름 · 이메일 — 문의 진입점)
└─ 업데이트·논의 탭 (항목별 게시판: 태그 4종 + 좋아요)
```

**개발 연동 노트**: 항목 상세 조회 API + 게시판·후기·좋아요 API(0.9 스키마안). 이미지 배열은 업로드 스토리지 URL 배열로 전환. 조회수 집계는 인기 정렬·통계의 소스가 되며 서버 집계로 전환한다(0.9). 스크랩 토글은 멱등 PUT/DELETE `/api/v1/scraps/:itemId`(0.10). 후기·게시판 글 등록은 항목 소유자에게 알림(kind `후기등록`/`게시판글`)을 발생시키는 지점이다(서버 책임).

## USR-05 신규 항목 등록 신청 (ProjectRegisterPage, /register)

**정의·역할**: 7개 카테고리의 신규 자산을 등록 신청하는 3단계 폼. 카탈로그 데이터 품질이 결정되는 수집 관문.

**목적**: 일반 사용자가 5~10분 안에 신청을 완료할 수 있게 하면서, 재사용 판단에 필요한 최소 정보를 표준 구조로 수집한다.

**기획 의도**: 설계 원칙은 **"등록 문턱이 낮아야 물량이 쌓이고, 물량이 쌓여야 카탈로그가 산다"**이다. 그래서 입력 항목은 만든 사람이라면 누구나 답할 수 있는 것으로만 구성했다 — 제목·요약·설명·사진·담당자, 그리고 유형별 한두 가지. 노드 구성이나 커넥터 등급처럼 도구 내부 지식이 필요한 전문 항목은 받지 않는다(그 정보량은 사진 최대 10장과 "언제 실행되고 어떤 순서로 동작하는지"를 묻는 상세 설명이 대신한다). 단계는 3개다: 무엇을 올릴지 고르고(카테고리), 내용을 쓰고(입력), 확인 후 신청한다 — 화면 이동이 적을수록 이탈이 적다.

**화면 동작**
- Step 0: 카테고리 카드 7종 중 하나를 클릭 → Step 1로 진행. AI Model 카드는 관리자에게만 보인다. AI 프로젝트 카드에는 "(일반 IT 시스템 구축 과제는 제외)" 경계 문구가 있다.
- Step 1 (단일 페이지 스크롤):
  - 사진 업로드: 파일 선택(복수) → 캐러셀 미리보기에 추가, 좌우 넘김·개별 삭제 가능. 10장 초과 선택 시 앞 10장만 반영되고 안내가 표시된다.
  - n8n을 선택한 경우: .json 파일을 업로드하면 → 파싱되어(`parseN8nJson`) 워크플로우 다이어그램 미리보기가 자동 표시된다. 예상 효과는 값+주기 입력(`TimeSavedInput`), 난이도는 선택.
  - Power Automate: 예상 효과 입력. 사진 영역에 "플로우 디자이너 화면 캡처 권장" 힌트가 표시된다.
  - 나만의 비서: 공유 프롬프트(텍스트 영역)·기반 모델(선택 칩).
  - AI Model(관리자만 도달 가능): 가용 여부·강점·모델 접속 URL·세부 모델명·글 분량·비용 등급 입력. 제목 placeholder는 모델명 단독 예시.
  - 필수 항목 미입력 시 다음 단계 버튼이 비활성 또는 검증 안내.
- Step 2: 입력 요약을 보여주고, "신청이 접수되면 {PREFIX}-{연도}-{순번} 형식의 고유 ID가 발급됩니다"와 승인 절차(신청 → 관리자 검토 → 승인 → 게시)를 안내한다. 신청 버튼 → 완료 화면(발급 ID 표시, 데모는 `makeItemId` 모사) → 내 현황으로 이동 가능.
- 이전 단계로 돌아가도 입력값이 유지된다.

**지켜야 할 룰**
- 3단계 고정: Step 0 카테고리 선택 → Step 1 내용 입력(공통 + 유형별 + 담당자 통합) → Step 2 최종 확인.
- 공통 필수: 제목, 한 줄 요약, 상세 설명, 담당자(부서·이름·이메일). 공통 선택: 사진 최대 10장, 업무 도메인, 태그.
- 유형별 세부: n8n(JSON 업로드+예상 효과+난이도) / PA(예상 효과) / 비서(공유 프롬프트+기반 모델) / AI Model(가용+강점+모델 접속 URL+세부 모델명+글 분량+비용) / ML(모델 유형+학습 데이터+개발 도구) / Vibe·AI 프로젝트(공통 항목만, 블로그 방식).
- 관계사 선택·운영 상태 입력·실행 URL 입력을 두지 않는다(예외: AI Model 모델 접속 URL).
- 폼 안정성: 모든 서브컴포넌트·스타일 객체는 모듈 레벨 정의(입력 포커스 손실 방지 — 확립된 구현 규칙).

**화면 구조**
```
등록 신청
├─ 스텝 인디케이터 (0 카테고리 → 1 내용 → 2 확인)
├─ Step 0: 카테고리 카드 7종 (AI Model는 관리자에게만 노출)
├─ Step 1: 내용 입력 (단일 페이지, 섹션 배치)
│  ├─ 사진 업로드 (캐러셀 미리보기·개별 삭제)
│  ├─ 제목 / 한 줄 요약 / 상세 설명
│  ├─ 유형별 세부 섹션
│  ├─ 업무 도메인 · 태그
│  └─ 담당자 정보
└─ Step 2: 최종 확인 (입력 요약 + ID 발급·승인 절차 안내 + 신청)
```

**개발 연동 노트**: 등록 API에서 서버가 ID 발급(0.3), AI Model 등록의 관리자 권한 재검증, 이미지 업로드 처리(별도 업로드 엔드포인트 + URL 참조 권장), 예상 효과 표준 문자열 검증을 담당한다. 신청 레코드는 승인 슬롯 0/2 상태로 생성되며, 접수 시 신청자에게 알림(kind `신청접수`)을 발생시킨다(서버 책임).

## USR-06 수정 요청 (EditRequestPage, /edit-request/:id)

**정의·역할**: 게시된 항목의 내용 수정을 신청하는 폼. 등록 폼 Step 1과 1:1 대응 구조로, 현재 값이 프리필된 상태에서 고쳐 제출한다.

**목적**: 게시 항목의 정보 최신성을 유지하되, 게시물 무결성을 위해 직접 수정이 아닌 신청·검토 절차를 거치게 한다.

**기획 의도**: 게시된 카탈로그 항목은 여러 사용자의 판단 근거가 되므로 등록자 임의 수정을 허용하지 않는다. 대신 수정 요청 → 관리자 검토 흐름으로 변경 이력이 관리 가능하게 했다. 폼을 등록 Step 1과 동일 구조로 유지하는 이유는 두 가지다: 사용자가 새 폼을 배울 필요가 없고, 입력 체계가 바뀔 때 두 폼을 함께 고치도록 강제되어 유지보수가 어긋나지 않는다.

**화면 동작**
- 진입 시 대상 항목의 현재 값이 전 필드에 채워져 표시된다(프리필). 사용자는 바꿀 부분만 고친다.
- 사진·JSON 업로드 등 입력 동작은 등록 폼과 동일(캐러셀·다이어그램 미리보기 포함).
- 수정 사유를 적고 제출 → 관리자 검토 대기열로 전송 → 완료 안내. 검토·반영은 ADM-02와 동일 골격.

**지켜야 할 룰**
- 필드 구성은 등록 폼 Step 1과 1:1 동일(간소화 7유형 체계). 삭제된 개념의 수정 UI를 두지 않는다.
- 현재 항목 값 프리필 필수. 수정 사유 입력 필수.
- AI Model 항목의 수정 요청은 관리자 전용.
- **인바운드 진입점(2곳 이상 유지)**: ① 항목 상세 헤더의 "수정 요청" 버튼(USR-04) ② 내 현황의 게시됨 카드 "수정 요청" 버튼(USR-07). 두 경로 모두 `navigate('/edit-request/:id')`로 진입한다.

**화면 구조**
```
수정 요청
├─ 대상 항목 표시 (ID · 제목)
├─ 수정 폼 (등록 Step 1 미러: 사진/제목/요약/상세/유형별/도메인/태그/담당자)
├─ 수정 사유
└─ 제출 (→ 관리자 검토)
```

**개발 연동 노트**: 수정 요청은 원본과 분리된 레코드(diff 또는 전체 스냅샷)로 저장하고, 승인 시 원본에 반영한다. 처리(반영/보류) 시 신청자에게 알림(kind `수정요청처리`)을 발생시킨다 — 프론트 `handleSubmit`에 발송 TODO 주석이 있고 실제 생성은 서버 책임(0.10). 담당자 변경(퇴사·이동 대응)이 실무상 최다 수정 사유가 될 가능성이 높다.

## USR-07 내 현황 (MyStatusPage, /my-status)

**정의·역할**: 로그인 사용자의 신청 항목·승인 진행 현황·작성 후기를 모아 보는 개인 대시보드.

**목적**: "내 신청이 지금 어디까지 갔나"를 즉시 확인하게 하고, 반려 시 사유를 명확히 전달해 재신청을 돕는다.

**기획 의도**: 승인 절차가 있는 시스템에서 신청자의 최대 불만은 진행 불투명성이다. 병렬 2-슬롯 모델(0.7)을 신청자 관점에서도 그대로 보여줘 — 관계사 승인·전사 승인 각각의 완료 여부를 슬롯 인디케이터로 — "어디서 멈춰 있는지"를 숨기지 않는다. 이 화면은 순수 조회 + 반려 대응 진입점이며, 게시 후 내용을 바꾸고 싶으면 수정 요청(USR-06) 경로를 쓴다.

**화면 동작**
- 진입 시 내 신청 항목이 카드 리스트로 표시된다. 상단 승인 단계 탭(전체/대기/게시됨/반려) 클릭 → 즉시 필터링.
- 각 카드에 슬롯 인디케이터 2개(관계사 승인/전사 승인)가 완료 여부와 함께 표시된다. 게시된 항목의 카드 클릭 → 해당 상세 페이지로 이동(`categoryPathOf`로 경로 산출).
- 반려된 항목은 사유 박스에 반려 사유 원문이 표시되고, 재신청 진입 버튼이 제공된다.
- 하단에 내가 쓴 후기 목록이 표시되고, 후기 클릭 → 해당 항목 상세로 이동.

**지켜야 할 룰**
- 승인 단계 기반 탭/필터와 슬롯 인디케이터를 유지한다. 운영 상태 뱃지·상태 변경 UI를 두지 않는다(0.4).
- 반려 사유는 원문 그대로 표시한다.
- 카테고리별 요약 칩: n8n 난이도·예상 효과 / pa 예상 효과 / 비서 기반 모델 / AI Model 가용·비용 / ML 모델 유형 / vibe·AI 프로젝트 없음.
- 신청일·처리일 표시 유지.
- 카드 메타 줄 선두에 **카드 ID**를 공용 `CardIdTag`로 표시한다(이 줄에는 등록 부서가 없어 선두 배치, 0.3).
- 게시됨 카드에 **"수정 요청" 진입 버튼**을 둔다 → `/edit-request/:id`(USR-06). 게시 후 정보 정정 경로.

**화면 구조**
```
내 현황
├─ 승인 단계 탭 (전체 / 대기 / 게시됨 / 반려)
├─ 신청 항목 카드 리스트
│  ├─ 카테고리 뱃지 · 제목 · 요약 · 유형별 요약 칩
│  ├─ 승인 슬롯 인디케이터 (관계사 승인 / 전사 승인)
│  └─ 반려 시: 사유 박스 + 재신청 진입
└─ 내가 쓴 후기 목록
```

**개발 연동 노트**: 내 신청 목록 API 응답에 승인 슬롯 현황과 반려 사유가 포함되어야 한다. 운영 상태 변경 엔드포인트는 존재하지 않는다(0.4·0.9). 승인 진행·반려는 알림(kind `관계사승인`/`전사승인`/`반려`)과 짝을 이루며, 이 화면과 알림 벨은 같은 사건을 다른 밀도로 보여준다.

## USR-08 공통 내비게이션 (Navbar / Footer)

**정의·역할**: 전 사용자 화면 공통의 상단 내비게이션과 하단 푸터. 화면 간 이동과 외부 실행 환경 진입을 담당한다. 알림 벨(NotificationBell)과 개인화 진입(설정)도 이 셸에 얹혀 있다.

**목적**: 어느 화면에서든 탐색·등록·내 현황·외부 도구로 한 번에 이동하게 한다.

**기획 의도**: "플랫폼 바로가기" 드롭다운은 **카테고리 단위 외부 실행 환경 링크**다(n8n 서버, HK GPT 등). 카탈로그는 발견을, 실행은 각 플랫폼이 담당한다는 역할 분리를 내비게이션 차원에서 표현한 것이다(항목 단위 URL을 두지 않는 0.5와 짝을 이루는 설계). 관리자 진입점은 관리자에게만 노출해 일반 사용자의 인지 부하를 줄인다. **상단 메뉴 "이용 가이드"(USR-09)는 "지금 무엇을 어떻게 하면 되는지"를 즉시 안내하는 실용 진입로**다. 개념·배경을 설명하던 소개(구 USR-02, About)는 가이드와 역할이 중복되어 폐지되었고(2026-07 결번), 소개가 담던 "왜 AX Platform" 섹션은 가이드가 흡수했다 — 이에 따라 **푸터 "서비스 소개" 링크 항목은 제거**했다.

**화면 동작**
- 메뉴(카탈로그/이용 가이드/등록) 클릭 → 해당 화면 이동, 현재 경로의 메뉴가 강조된다.
- "플랫폼 바로가기" 클릭 → 드롭다운 열림. n8n 등 준비된 환경은 새 탭으로 외부 이동, 미준비 환경은 "준비 중" 비활성 표기(외부 환경의 준비 여부이며 항목과 무관).
- **알림 벨(NotificationBell)**: 로그인·비공유 모드에서 표시. 미읽음 뱃지 + 클릭 시 드롭다운(최근 5건·전체 읽음·항목 이동). 관리자 화면 상단 바(AdminNavbar)에도 동일 벨이 배치된다(0.10).
- 로그인 상태에서 아바타 클릭 → 메뉴(내 현황·**설정**·관리자 이동·로그아웃). 관리자에게만 관리자 진입 아이콘이 추가 표시된다.
- 로그아웃 → 세션 제거 후 로그인 화면으로.
- Footer의 운영 채널 링크 → Teams 채널 새 탭 이동. (구 "서비스 소개" 링크는 USR-02 폐지와 함께 제거됨.)

**지켜야 할 룰**
- 상단 메뉴는 "이용 가이드"(`/guide`)를 노출한다. 구 소개(`/about`)는 폐지되어 `/guide`로 리다이렉트하며, 푸터 "서비스 소개" 링크 항목은 두지 않는다.
- 아바타 드롭다운에 "설정"(`/settings`) 항목을 둔다.
- 아바타 드롭다운 헤더에 **본인 소속 관계사 표시명**을 1줄 표기한다(표시명 우선·코드 폴백, 조직 SSOT `orgCompanyName` 파생). companyAdmin은 담당 관계사를 병기한다. 이는 "본인 소속 안내"로 관계사 표시 폐기(0.5) 대상이 아니다.
- 알림 벨은 Navbar(로그인·비공유 모드)와 AdminNavbar 양쪽에 배치하며 동일 소스(`useNotifications`)를 쓴다.
- 외부 환경 URL은 `CATEGORIES`의 `accessUrl`에서 온다(ADM-06에서 편집).
- 운영 문의 채널은 Teams(`operations.ts`의 `TEAMS_CHANNEL_URL` 단일 상수).

**화면 구조**
```
Navbar: 로고 · 주요 메뉴(카탈로그/이용 가이드/등록) · 플랫폼 바로가기 드롭다운 · 알림 벨 · 아바타 메뉴(내 현황/설정/관리자/로그아웃)
Footer: 서비스 표기 · 사내 전용 고지 · 운영 채널 링크(Teams)
```

**개발 연동 노트**: 알림 벨은 `GET/PATCH /api/v1/notifications`(0.10)로 목록·읽음을 채운다. 나머지는 정적 라우팅·외부 URL 참조로 API 의존이 낮다.

## USR-09 이용 가이드 (GuidePage, /guide)

**정의·역할**: 처음 쓰는 직원 기준의 실용 안내 화면. Navbar 상단 메뉴 "이용 가이드"의 연결 대상이며, 랜딩 CTA "이용 가이드" 박스도 여기로 연결된다. "지금 무엇을 어떻게 하면 되는지"를 단계로 안내하며, 폐지된 소개(구 USR-02, About)의 개념·배경 도입부("왜 AX Platform")를 인트로로 흡수해 "왜"와 "어떻게"를 한 화면에 담는다.

**목적**: 로그인 직후의 사용자가 탐색 → 등록 → 승인 대기 → 문의까지의 실제 동선을 헤매지 않고 밟게 한다. 등록 심리 장벽을 "절차가 이렇게 간단하다"로 낮춘다.

**기획 의도**: 당초 소개(About)가 "왜/무엇을", 가이드가 "어떻게"로 나뉘어 있었으나, 두 화면의 독자가 사실상 같고(둘 다 처음 온 사용자) 역할이 겹쳐 **소개를 폐지하고 가이드로 통합**했다(2026-07). 가이드는 "왜 AX Platform인가" 도입부로 시작해 곧바로 시작하기·등록·승인의 "어떻게"로 이어진다 — 한 화면에서 동기와 행동을 잇는 편이 화면을 오가게 하는 것보다 자연스럽다. 코드/기술 용어는 배제하고 승인 절차는 병렬 2-슬롯(0.7)을 사용자 언어로 풀어 "순서 없이 두 승인이 모이면 게시"라는 핵심만 전한다. 디자인 토큰·서브컴포넌트는 모듈 레벨 단일 체계로 톤을 통일했다.

**이관 섹션(구 USR-02 흡수)**: "왜 AX Platform인가요?" — Problem→Solution 4조(흩어진 자산→한곳에 모은 카탈로그 · 중복 개발→먼저 찾고 재사용 · 무엇을 써야 할지 모름→질문에 답하는 콘텐츠 · 사례의 단절→우수 사례 전파)를 문구·구성 그대로 이관해 가이드 인트로(히어로 다음, 기존 첫 섹션 앞)에 배치했다. **섹션 부제만 확정 변경**했다: 기존 "현장의 네 가지 문제를, 네 가지 방식으로 해결합니다" → **"현장의 문제를, 한곳에 모으고, 찾고, 질문에 답하고, 좋은 사례를 전파하여 해결합니다"**. 카드 서브컴포넌트(`WhyCard`·`WhyIcon`)는 모듈 레벨로 이식했다.

**화면 동작**
- 스크롤 열람형 정적 화면. 인트로(왜 AX Platform) + 4개 단(① 시작하기 ② 등록 가이드 ③ 승인 절차 ④ FAQ)으로 구성된다.
- ① 시작하기: 로그인 → 탐색 → 상세 열람 → 담당자 문의의 기본 동선 안내.
- ② 등록 가이드: 등록 3단계 + 카테고리 유형별 입력 팁.
- ③ 승인 절차: 병렬 2-슬롯 승인(관계사 + 전사, 순서 무관, 반려 시 재신청) 설명.
- ④ FAQ: 등록 자격·승인 소요·수정 방법·문의처 등. (구 About FAQ의 고유 문항 "문의는 어디로 하나요?"를 편입, 별도 About 진입 링크는 제거.)
- CTA·링크는 실제 라우트(등록·목록 등)로 이동한다.

**지켜야 할 룰**
- 콘텐츠 근거는 본 기획설명서·등록/승인 실제 흐름이다. 소스와 어긋나는 절차 서술을 두지 않는다.
- 승인 절차는 병렬 2-슬롯(순서 무관, 2/2 게시)으로 서술한다 — 직렬 "1차/2차" 표현을 쓰지 않는다(0.7).
- 코드·기술 내부 용어를 노출하지 않는다(처음 쓰는 직원 기준).
- 이관 인트로("왜 AX Platform")의 카드 4조 문구는 원문 무변경, 섹션 부제만 확정 문구를 유지한다.
- 디자인은 모듈 레벨 토큰·서브컴포넌트 단일 체계를 준수한다.

**화면 구조**
```
이용 가이드
├─ 히어로 (한 줄 안내)
├─ 인트로: 왜 AX Platform (Problem→Solution 4조, 구 USR-02 흡수)
├─ ① 시작하기 (로그인 → 탐색 → 상세 → 문의)
├─ ② 등록 가이드 (3단계 + 유형별 팁)
├─ ③ 승인 절차 (병렬 2슬롯: 관계사+전사, 순서 무관, 반려 시 재신청)
└─ ④ FAQ (문의처 문항 포함)
```

**개발 연동 노트**: 정적 콘텐츠로 API 의존 없음. 절차 문구는 승인·등록 정책 변경 시 함께 갱신한다(본 문서와 정합 유지).

## USR-10 공지사항·업데이트 소식 (NoticesPage, /notices)

**정의·역할**: 공지사항·업데이트 소식을 종류별로 열람하는 공개 목록 화면(**인증 불필요**). 랜딩 최신소식 섹션 "더보기"의 연결 대상이다. 관리자(ADM-09)가 작성·관리한 소식을 사용자에게 보여주는 읽기 전용 채널이다.

**목적**: 플랫폼 운영 소식(정책 안내·기능 업데이트)을 한곳에 모아, 사용자가 "무엇이 바뀌었나"를 확인하게 한다.

**기획 의도**: 공지는 **브로드캐스트**이지 개인 알림이 아니다(0.10). 그래서 개인 알림 벨과 축을 분리해 별도 공개 페이지로 두고, 로그인 없이도 볼 수 있게 했다 — 소식은 특정 사용자의 활동이 아니라 전원 대상 안내이기 때문이다. 랜딩 최신소식과 이 목록은 **동일 소스·동일 표시 규칙**(공지 단일 소스 `noticeMockData`)을 공유해, 두 곳의 내용이 어긋나지 않는다(랜딩은 추가로 탭별 5건으로 제한). 종류를 공지사항/업데이트 2종으로만 나눈 것은 "지켜야 할 안내"와 "새로워진 것"의 성격이 다르기 때문이다.

**화면 동작**
- 종류 탭 2종(공지사항/업데이트) 전환 → 해당 종류의 소식만 표시. 항목 클릭 시 본문이 펼쳐진다(단일 아코디언, `expanded`).
- 표시 규칙: `visible=true`인 소식만, **pinned(고정) 우선 + 게시일 최신순**(`visibleNoticesByKind` 헬퍼, 랜딩과 동일).
- URL 파라미터 `?kind=`: 진입 탭을 결정(공지사항이 기본). 탭 전환 시 `?kind=`를 `replace`로 동기화(공지사항 탭이면 파라미터 제거).
- `Navbar` + `Footer` 셸을 쓴다.

**지켜야 할 룰**
- 공개 페이지(인증 불필요). 관리 기능(작성·수정·삭제·토글)은 두지 않는다 — 관리는 ADM-09 전용.
- 종류는 `NOTICE_KINDS` 2종(공지사항/업데이트)만.
- `visible=true`만 노출, pinned 우선 + 최신순. 비노출(visible=false) 소식은 사용자 목록에 나타나지 않는다.
- 랜딩 최신소식과 동일 소스·동일 헬퍼를 사용한다(중복 정의 금지, 0.10·USR-00).
- `?kind=` 파라미터 외 정의되지 않은 파라미터는 무시한다.

**화면 구조**
```
공지사항·업데이트 소식
├─ 종류 탭 (공지사항 / 업데이트)
└─ 소식 목록 (고정 우선 · 최신순)
   └─ 각 행: 종류 뱃지 · 제목 · 게시일 · (클릭 시 본문 펼침)
```

**개발 연동 노트**: 사용자 공개 목록은 `GET /api/v1/notices`(visible=true만). 관리자 전체 목록(비노출 포함)은 ADM-09의 `GET /api/v1/admin/notices`와 구분한다. Notice는 알림을 발생시키지 않는다(0.10 확정).

## USR-11 설정 (SettingsPage, /settings)

**정의·역할**: 로그인 사용자의 관심사(관심 카테고리·관심 업무 도메인)를 설정하는 개인 화면(`ProtectedRoute`). 저장한 관심사는 랜딩 개인화 패널의 맞춤 추천 근거가 된다. 진입 경로는 개인화 패널 퀵메뉴 "설정" + Navbar 아바타 드롭다운 "설정" 2곳.

**목적**: 사용자가 관심 축을 한 번 지정해 두면, 이후 방문마다 개인화 패널이 관심사에 맞는 항목을 우선 보여주게 한다.

**기획 의도**: 추천은 "무엇을 좋아하는지"를 알아야 성립한다. 행동 로그 기반 암묵 추천은 데이터가 쌓이기 전에는 빈약하므로, 우선 **명시적 관심사 선언**(카테고리·도메인 다중 선택)으로 콜드스타트를 해결한다. 설정을 별도 화면으로 둔 이유는 향후 개인 정보 항목(프로필·알림 수신 설정·표시 환경)이 여기로 확장될 자리이기 때문이다 — 지금은 관심사만이지만 확장 지점을 TODO로 명시해 뒀다.

**화면 동작**
- ① 관심 카테고리: `CATEGORIES` 7종 칩 다중 선택. ② 관심 업무 도메인: `BUSINESS_DOMAINS` 6종 칩 다중 선택.
- 폼 로컬 상태에서 편집 → **저장 버튼** 클릭 → `useInterests().save`로 localStorage `ax_user_interests`에 기록 → **저장 완료 인라인 피드백**.
- 저장 즉시 개인화 패널 추천이 갱신된다(`useSyncExternalStore` 구독, 0.10).
- 안내 문구: "추후 개인 정보 항목이 추가될 수 있습니다. (프로필·알림 수신 설정 등)" + 파일 상단 확장 지점 TODO.

**지켜야 할 룰**
- 관심 카테고리는 `CATEGORIES`(7종), 관심 도메인은 `BUSINESS_DOMAINS`(6종)에서 파생한다(개별 하드코딩 금지).
- 저장은 명시적 버튼으로 확정하고 저장 완료를 인라인으로 피드백한다(팝업·모달 신설 금지 — 코딩 규약).
- 관심사 저장 소스는 localStorage `ax_user_interests` 단일 키(0.2·0.10).
- 향후 확장 항목(프로필·알림 수신·표시 환경)은 TODO로만 두고 이번 범위에서 구현하지 않는다.

**화면 구조**
```
설정
├─ ① 관심 카테고리 (7종 칩 다중 선택)
├─ ② 관심 업무 도메인 (6종 칩 다중 선택)
├─ 저장 버튼 (+ 저장 완료 인라인 피드백)
└─ 안내 (향후 개인 정보 항목 확장 예정)
```

**개발 연동 노트**: 저장은 **PUT `/api/v1/me/interests`**, 프리필은 `GET /api/v1/me`, 추천은 `GET /api/v1/me/recommendations`(관심사 매칭, 0.10). 관심사 매칭 규칙(카테고리 또는 도메인 일치 → `views`→`likes` 상위 12)은 서버 이관 시 동일 규칙을 유지한다.

# PART 2. 관리자 화면

관리자 화면 공통: 사이드바 콘솔 레이아웃(사용자 화면의 폭 표준과 별개). 사이드바에 검토 대기 건수 뱃지(pendingCount)가 표시되며, 이 값은 조회 범위 선택과 무관하게 **권한 범위(baseScope) 기준**으로 고정된다 — 조회는 자유롭게 바꿔도 "내가 처리해야 할 건수"는 흔들리지 않아야 하기 때문이다. 관리자 화면 상단 바(AdminNavbar)에도 알림 벨(NotificationBell)이 배치된다(0.10).

## ADM-01 관리자 대시보드 (AdminDashboard, /admin)

**정의·역할**: 전사관리자·관계사관리자 공용의 관리 진입점. KPI, 승인 대기·최근 승인 목록, 등록 추이·분포를 한눈에 보여준다.

**목적**: 관리자가 로그인 직후 "지금 처리할 것이 무엇인지(승인 대기)"와 "플랫폼이 어떻게 크고 있는지(추이)"를 즉시 파악하게 한다.

**기획 의도**: 핵심 설계는 **권한 범위(baseScope)와 조회 범위(viewScope)의 분리**다. 관계사관리자도 전사 현황을 조망할 수 있어야 하지만(맥락 파악), 처리 책임(대기 건수)은 자기 권한 범위로 고정되어야 한다. 조회는 유연하게, 책임은 고정으로. KPI의 "게시된 도구"는 승인 완료(게시) 기준 집계다 — 운영 상태 개념이 없으므로(0.4) "쓸 수 있는 도구 수" 같은 상태 기반 지표는 성립하지 않고, 게시 여부가 유일한 객관 기준이다.

**화면 동작**
- 진입 시 자기 권한 범위 기준 KPI·목록·차트가 표시된다.
- 조회 범위 선택기(AdminScopeSelect): 전사관리자에게 항상 표시. 관계사관리자는 담당 관계사가 2곳 이상일 때만 선택기가 나타나고, 1곳이면 고정 뱃지, 0곳이면 "담당 관계사가 지정되지 않았습니다 — 전사관리자에게 문의하세요" 배너가 표시된다.
- 조회 범위를 바꾸면 → KPI·차트·목록이 그 범위 기준으로 갱신된다. 단 사이드바 대기 건수는 변하지 않는다(baseScope 고정).
- **기간 선택기 없음**: 대시보드는 고정 스냅숏 화면이다(기간 필터 UI·state 제거). 위젯별 기준은 고정되어 있다 — 누적 위젯(전체 등록물·게시된 도구·누적 활용 후기·카테고리 구성·도메인 분포) = 전체 기간 누적, "이번 달 신규" = 당월 `createdAt` 실측, "승인 대기"·"최근 승인" = 현재 큐/게시 카탈로그 최신순, "월별 등록 추이" = **최근 12개월 고정**(현재월 파생). 기간 스코핑이 필요한 상세 분석은 통계(ADM-04)에서 수행한다.
- 승인 대기 목록의 건 클릭 → 등록 검토 화면(ADM-02)의 해당 건으로 이동.

**지켜야 할 룰**
- KPI 5종: 전체 등록물 / 승인 대기(부분 승인 포함) / 이번 달 신규 / 게시된 도구 / 누적 활용 후기.
- 카테고리별 분포의 색·라벨은 `CATEGORIES` 파생(7종, AI 프로젝트 포함).
- 목록의 카드 ID는 `{PREFIX}-{YYYY}-{NNN}` 형식. 데모 목업 ID는 카탈로그 SSOT와 충돌하지 않도록 관리한다(동일 ID·상이 제목 금지, 0.9).

**화면 구조**
```
대시보드
├─ 헤더 (역할별 eyebrow + 조회 범위 선택기/담당 뱃지) — 기간 선택기 없음(고정 스냅숏)
├─ KPI 카드 × 5
├─ 승인 대기 목록 (→ 검토 화면 진입)
├─ 최근 승인 목록
└─ 차트: 등록 추이 · 카테고리별 분포 · 도메인 분포
```

**개발 연동 노트**: 대기·최근 승인·통계 API는 `?company=` 범위 파라미터를 받되, 범위 한정은 **서버 사이드 필터링**이 원칙이다(클라이언트 필터 금지 — 권한 신뢰 경계). 등록 추이 API는 기간 파라미터 `&from=YYYY-MM&to=YYYY-MM`(inclusive)를 추가로 받는다(대시보드 데이터 계약 `GET /api/v1/admin/stats/dashboard?company=:codes&from=YYYY-MM&to=YYYY-MM`) — 대시보드에는 기간 선택기가 없으므로 이 창은 클라이언트가 **최근 12개월 고정**(`recentMonthsRange(12)`, 현재월 파생)으로 정하고, 나머지 위젯은 range를 주지 않는 누적 스냅숏이다. 데모 수치는 모두 자산 SSOT에서 파생한다(합성 관계사 테이블 폐기) — 승인 대기는 검토 큐(`getReviewQueue`), 최근 승인은 게시 카탈로그 최신순, "게시된 도구"·"누적 활용 후기"는 `ownerCompany` 파생, 등록 추이는 `createdAt` 파생(기간 범위 위 0-fill 연속 월축). 전 화면 총량이 카탈로그와 일치한다(0.9 총량 일치 원칙).

## ADM-02 등록 검토 (AdminReview, /admin/review)

**정의·역할**: 등록 신청·수정 요청을 검토해 슬롯 승인 또는 반려하는 화면. 승인 워크플로우(0.7)의 실행 지점.

**목적**: 검토자가 신청 내용 전체를 한 화면에서 확인하고, 자기 권한에 해당하는 슬롯을 처리하게 한다.

**기획 의도**: 병렬 2-슬롯 구조(0.7)의 목적은 승인 병목 제거다 — 관계사 관리자와 전사 관리자가 서로를 기다리지 않는다. 검토 패널의 표시 필드는 등록 폼과 동일한 체계로 맞춘다 — 신청자가 쓴 것과 검토자가 보는 것이 어긋나면 반려 사유가 엉뚱해진다. 검토자가 항목의 관계사를 지정하는 절차는 없다(전 항목 전사 공용, 0.5).

**화면 동작**
- 좌측 대기 목록에서 건을 클릭 → 우측 패널에 신청 내용 전체(이미지 캐러셀, n8n이면 다이어그램, AI Model면 모델 사양 포함)와 승인 이력, 슬롯 카드 2개가 표시된다.
- 자기 자격에 해당하는 슬롯의 승인 버튼 클릭 → 확인 → 해당 슬롯 완료 처리, 승인 이력에 기록. 한 슬롯만 완료되면 항목은 "부분 승인" 상태로 대기 유지, 두 슬롯이 모두 완료되는 순간 게시로 전환된다.
- 자격이 없는 슬롯은 비활성이며 사유가 안내된다(예: "전사 공용 항목은 전사관리자만 처리할 수 있습니다"). 자격 판정은 원본 항목 기준(0.6).
- 반려 버튼 → 사유 입력(필수) → 확정 시 반려 처리, "사유는 신청자에게 그대로 전달됩니다" 안내.
- 검토 중 값 보정(예: 예상 효과 표기 정리)은 임시 보관되었다가 승인 시 정리 저장된다.
- 상단 유형(kind) 필터·검색으로 대기 목록을 좁힐 수 있다.
- **승인 취소**(게시 전 한정): 이미 승인된 슬롯의 카드에 "승인 취소" 버튼이 노출된다 — 노출 조건은 ① 게시 전(부분 승인) ② 본인 권한 슬롯(관계사 슬롯 = 등록 주체 담당 관리자·전사 슬롯 = 전사관리자, 가시성/승인과 동일 predicate). confirm 1단계 → 슬롯을 "대기"로 되돌리고 승인 단계를 재판정(부분 승인 → 승인 대기). **게시 완료(2/2) 건에는 노출하지 않는다** — 게시물 정정은 "중지" 경로를 쓴다.
- 목록·상세 메타에 **등록 관계사 배지**(등록 주체 `ownerCompany`의 표시명)를 노출한다 — 표시명은 조직 SSOT(`orgCompanyName`) 파생(신규 매핑 리터럴 금지). 이는 관리자 화면 전용이며 사용자 화면에는 어떤 관계사 배지도 두지 않는다(0.5).

**지켜야 할 룰**
- 좌측 대기 목록 + 우측 상세 검토 패널 구조.
- 검토 큐 가시성: 관계사관리자는 신청 등록 주체(ownerCompany)가 본인 담당 관계사인 건만 본다(항목의 노출 범위가 아니라 등록 주체가 판정 축 — 관계사 슬롯은 신청자 소속 관계사 관리자의 몫). 전사관리자는 전체. 헤더 건수·빈 상태 문구도 이 가시 집합과 정합.
- 슬롯 처리 자격: 관계사 슬롯 = 신청 등록 주체 관계사의 담당 관리자(가시성과 동일 축), 전사 슬롯 = 전사관리자.
- 반려 사유 필수, 원문 전달 안내 유지. 승인 이력(누가·어느 슬롯·언제·사유) 표시.
- 검토 표시 필드는 등록 폼 체계와 1:1. 등록 폼에 없는 입력 개념을 검토 화면에 만들지 않는다.

**화면 구조**
```
등록 검토
├─ 좌: 대기 목록 (유형 필터 · 검색 · 카드: 유형/제목/부서/신청자)
└─ 우: 상세 검토 패널
   ├─ 메타 (유형 · 승인 단계 뱃지 · 등록 관계사 배지 · ID · 신청 정보)
   ├─ 승인 이력 (승인 / 반려 / 취소)
   ├─ 신청 내용 (등록 폼 체계 필드 전체)
   ├─ 슬롯 카드 × 2 (관계사 승인 / 전사 승인 — 각자 승인 버튼 · 승인된 슬롯은 게시 전 "승인 취소")
   └─ 반려 (사유 입력 → 반려 확정)
```

**개발 연동 노트**: 승인/반려/취소 API body에 슬롯 식별을 포함한다(`company`·`companyScope`는 body에 넣지 않음 — 서버 내부 데이터). 승인 이력(`approval_history`) action은 **3종(approve/reject/cancel)** 이며 기록 + 슬롯 상태 갱신 + 게시 전환 판정(2/2)은 트랜잭션으로 묶고, 슬롯 자격은 서버에서도 재검증한다(취소도 동일 자격 가드 + 게시 전 상태 확인). 슬롯 승인(`approveSlot`, kind `관계사승인`/`전사승인`·2/2 게시 문구)·반려(`handleReject`, kind `반려`)·승인 취소(`cancelSlot`)는 신청자 알림 발생 지점으로 프론트에 발송 TODO 주석이 있으며, 실제 생성은 서버 책임(0.10).

## ADM-03 카드 관리 (舊 항목 관리·프로젝트 관리, AdminProjectManage, /admin/projects)

**정의·역할**: 게시·반려 포함 전체 항목의 조회·편집·삭제를 담당하는 관리 화면.

**목적**: 담당자 변경, 오기 수정, 정책 위반 항목 처리 등 게시 후 운영 이슈를 관리자가 직접 해결하게 한다.

**기획 의도**: 수정 요청(사용자 주도, USR-06)과 별개로 관리자 직접 편집 경로가 필요하다 — 퇴사자 담당자 교체처럼 원 등록자가 신청할 수 없는 케이스가 있기 때문이다. 편집 가능 필드는 등록 폼과 동일한 체계로 제한한다 — 관리자 편집이라도 데이터가 스키마를 벗어나면 안 된다. `canManageItem` 원본 기준 판정(0.6)이 이 화면의 보안 핵심이다.

**화면 동작**
- 목록은 카테고리 그룹 아코디언(그룹 헤더·건수·접기/펼치기, 기본 전체 접힘 + 선택 항목 소속 그룹만 펼침, 검색 시 매칭 그룹 자동 펼침)으로 구성한다. 항목 선택 → 편집 패널에 현재 값이 로드된다. 권한 밖 항목(담당 관계사가 아닌 항목·전사 공용 항목에 대한 관계사관리자)은 편집 불가로 표시된다.
- 필드 수정 후 저장 → 즉시 반영(연동 후 서버 저장). 예상 효과는 값·주기 분리 입력으로 편집되고 저장 시 표준 문자열로 직렬화된다.
- 이미지는 수정 모드에서 등록 폼과 동일한 방식으로 추가(파일 선택 → 미리보기)·개별 삭제한다(최대 10장, 데모 data URL·서버 업로드는 백로그). 조회 모드는 캐러셀 표시 전용.
- 미선택 상태에는 총 건수·카테고리 분포 요약 플레이스홀더를 표시한다.
- 삭제 버튼 → 확인 절차를 거쳐 삭제.

**지켜야 할 룰**
- 편집 필드는 등록 폼 체계와 동일. 운영 상태·관계사 편집 UI를 두지 않는다.
- 권한: 관계사관리자는 담당 관계사 항목만, 전사 공용은 전사관리자만. 판정은 항상 원본 기준(이중 가드).
- 목록·상세 헤더 메타에 **등록 관계사 배지**(등록 주체 `ownerCompany` 표시명, 조직 SSOT `orgCompanyName` 파생)를 노출한다 — 관리자 화면 전용(사용자 화면 노출 금지, 0.5).
- 삭제는 확인 절차 필수.

**화면 구조**
```
카드 관리
├─ 목록 (검색 · 유형 필터 · 승인 단계 표시)
└─ 편집 패널 (등록 체계 필드 편집 + 담당자 교체 + 삭제)
```

**개발 연동 노트**: 편집 API body에서 `company`·`companyScope` 제외. 편집 이력 로깅 권장(감사 대응).

## ADM-04 통계 (AdminStatistics, /admin/statistics)

**정의·역할**: 등록·활용 현황의 집계 리포트 화면. 운영 성과 보고의 근거 자료.

**목적**: "카탈로그가 실제로 확산되고 있는가, 얼마나 절감 효과를 내는가"를 정량으로 보여준다.

**기획 의도**: 타사 AX 관리 시스템 벤치마킹(SKT AXMS)에서 확인한 교훈은 "성과가 숫자로 보여야 확산이 굴러간다"는 것이다. 절감 시간은 연간 환산으로 집계하되, 원본 자유 텍스트를 보존하고 환산 불가한 값은 부풀리지 않고 "추정 불가"로 분리 표기한다 — 경영 보고 수치의 신뢰가 이 정직함에서 나온다. 분석 축은 실제로 입력받는 데이터에만 둔다: 난이도는 n8n에만 입력이 있으므로 n8n 전용 축, 비용 등급은 AI Model, 모델 유형은 ML. 입력이 없는 축을 만들면 빈 차트만 남는다. (조회수도 같은 원칙에서 통계 축으로 만들지 않는다 — 인기 정렬·랜딩 트렌딩의 소스일 뿐 성과 지표가 아니다, 0.9.)

**화면 동작**
- 진입 시 권한 범위 기준 요약 카드·차트가 표시된다. 조회 범위 선택기 동작은 ADM-01과 동일(baseScope/viewScope 분리).
- 범위 변경 → 전 차트·카드 갱신. 카테고리별 현황의 색·라벨은 `CATEGORIES` 파생으로 목록·상세와 항상 일치한다.
- 기간 선택기(AdminPeriodSelect, ADM-01과 달리 통계 전용): 확정 4종 — **최근 3개월** / **최근 6개월** / **올해 전체**(현재 연도 1월~현재 월, 시스템 현재월 파생) / **범위 지정**(시작 월~종료 월, 최대 24개월). 기본값 "올해 전체". **전 기간 프리셋은 없다** — 레거시 2024 데이터는 범위 지정으로만 조회한다(시작 하한 2024.07). 통계 화면에서는 **전 집계**(요약 카드·카테고리 현황·도메인·부서·난이도/비용/모델 유형·절감 효과·태그·후기 TOP5·월별 추이)가 선택 기간(`createdAt` 기준)에 정합한다. "이번 달 신규" 카드만 당월 고정(기간 무관). 월별 추이 x축은 선택 범위의 월을 연속으로 표시하고 빈 월은 0으로 채우며, 24개월까지 라벨(YY.MM)이 겹치지 않도록 표기 밀도를 자동 조정한다(14개월 초과 시 라벨 간격 2).
- 부서별 현황·비즈니스 도메인 분포는 기본 **상위 5개(TOP 5)만 표시** + "외 N개" 표기이며, 상자 클릭 또는 헤더 "전체 보기 (N)" 토글로 같은 상자가 전체 목록으로 펼쳐진다(재클릭·"접기"로 복귀). 접힘/펼침과 무관하게 막대 분모(전량 합계·최댓값)는 동일해 합계가 불변이다(상위 5 + 외 N = 전체). 두 차트는 공용 컴포넌트 1개(`CollapsibleRankChart`)를 공유한다 — 도메인은 현재 6종이지만 SSO 연동 후 부서·도메인 급증에 분기 없이 대응하려 동일 패턴을 적용한다.
- 절감 효과 요약: 연간 환산 총량 + 집계 가능 건수 + 추정 불가 건수 3종이 함께 표시된다.

**지켜야 할 룰**
- 절감 효과 3종 세트(연간 환산·집계 가능·추정 불가) 유지.
- 축: 카테고리(7종) · 도메인 · 난이도(n8n 전용) · 비용 등급(AI Model) · 모델 유형(ML) · 태그 빈도. 운영 상태 분포 축·조회수 축을 두지 않는다.
- 태그 빈도 축은 카드에 부착된 태그(SSOT `tags`) 집계다 — 사용자가 검색한 실제 탐색 키워드가 아니다. 탐색 키워드 측정은 서버 검색 로그 기반으로 Phase 2에서 별도 제공한다(부록 B).
- 도메인 분석 축은 `BusinessDomain` 6종(영업·생산·연구·재무·HR·IT)에 정합한다(관리자 분석의 세부 라벨도 6종으로 통일).
- 기간 프리셋 확정 4종(최근 3개월·최근 6개월·올해 전체·범위 지정). "올해 전체"는 현재 연도만 표시(2024·2025 등 이전 연도 미표시) — 라벨과 동작이 일치해야 한다. **전 기간 프리셋 없음**: 레거시 2024 구간은 범위 지정으로만 도달한다. 범위 지정은 데이터 존재 구간(2024.07~현재 월)에서 시작~종료 선택, **최대 24개월**(초과 시 종료를 시작+23개월로 절단, 종료<시작은 자동 스왑 — UI는 종료 옵션 창을 [시작, 시작+23개월]로 제한해 선택 단계에서 강제). 기간 필터는 파생 계층 1곳(`statsDerive`/`dataSource`)에서 `createdAt` 기준으로 수행하고 화면별 개별 필터를 두지 않는다.
- 부서별 현황·비즈니스 도메인 분포는 기본 TOP 5 표시 + 전체 펼치기(공용 `CollapsibleRankChart` 1개, 중복 구현 금지). 접힘/펼침 합계 불변(상위 5 + 외 N = 전체).
- 집계 데이터는 성과 평가 용도가 아님(0.1 원칙, 화면 워딩에도 반영).

**화면 구조**
```
통계
├─ 헤더 + 조회 범위 선택기 + 기간 선택기(프리셋 4종 / 범위 지정 최대 24개월)
├─ 요약 카드 (총 등록 · 이번 달 신규 · 참여 부서 · 참여 관계사)
├─ 카테고리별 등록 현황 (7종)
├─ 월별 추이 (선택 범위 연속 월축, 24개월 라벨 밀도 자동 조정)
├─ 비즈니스 도메인 분포 · 부서별 현황 (TOP 5 + 전체 펼치기, 공용 패턴)
├─ 절감 효과 요약 (연간 환산 + 추정 불가 분리)
├─ 등록 항목 분석 (난이도/비용/모델 유형 축)
├─ 후기 많은 카드 TOP 5 (누적 후기 수 기준)
└─ 태그 빈도 (SSOT tags 집계 상위)
```

**개발 연동 노트**: 서버 집계 API(`?company=` 범위 + 기간 `&from=YYYY-MM&to=YYYY-MM` inclusive, 계약 초안 `GET /api/v1/admin/stats?company=:codes&from=YYYY-MM&to=YYYY-MM`). 모든 수치는 자산 SSOT·후기에서 파생한다(합성 관계사 테이블 폐기 — `lib/statsDerive`) — 등록 추이는 `createdAt` 파생(카테고리 스택), 도메인·부서·난이도·비용·ML 유형·태그 빈도는 카탈로그 실측, 후기 TOP5는 후기 SSOT 누적, 절감 효과는 `expectedTimeSaved` 보유 카드(n8n·PA) 연간 환산. 절감 시간 환산 로직(`parseTimeSaved`)은 화면에서 파생 계층으로 이동했으며 서버 이관 시 동일 규칙 유지(STRUCTURE.md의 정규화 규칙 참조). 통계 소스 키(`SourceKey`)는 7종. 도메인 분포는 `BusinessDomain` 6종 기준.

## ADM-05 분류 체계 관리 (AdminTaxonomy, /admin/taxonomy)

**정의·역할**: 고정 분류(Controlled Vocabulary)와 자유 태그를 관리하는 화면.

**목적**: 검색·필터·통계의 축이 되는 분류 값을 표준화하고, 자유 태그의 난립을 관리한다.

**기획 의도**: 분류 설계 원칙은 "고정 분류 위주"다 — 검색·필터·(향후) RAG 모두 통제된 어휘가 있어야 품질이 나온다. 자유 태그는 등록 문턱을 낮추는 보조 수단이며, 유의미하게 반복되는 태그는 관리자가 고정 분류로 승격(편입)하는 운영 루프를 상정한다. 관리 대상 분류는 등록 폼에서 실제로 입력받는 축과 정확히 일치시킨다 — 입력이 없는 분류는 관리 부담만 남긴다.

**화면 동작**
- 탭(업무 도메인/구성 난이도/비용 등급/ML 모델 유형) 전환 → 해당 분류의 값 목록과 사용 건수가 표시된다.
- 값 추가·수정·삭제 가능. 삭제 시도 시 사용 중인 항목 수와 함께 유의사항이 안내된다.
- 자유 태그 관리: 빈도순 태그 목록에서 태그를 골라 고정 분류로 편입할 수 있다.

**지켜야 할 룰**
- 탭 4종: 업무 도메인 / 구성 난이도(n8n 전용 명시) / 비용 등급(AI Model) / ML 모델 유형. + 자유 태그 관리.
- 운영 유의사항: "고정 분류 항목 삭제 시 해당 분류가 지정된 기존 항목은 공란 처리될 수 있음. 삭제 전 사용 중인 항목 수 확인."
- 자유 태그의 출처(sourceKind)는 7개 카테고리 대응.

**화면 구조**
```
분류 체계 관리
├─ 고정 분류 탭 4종 (값 목록 · 추가/수정/삭제 · 사용 건수)
├─ 자유 태그 관리 (빈도 · 고정 분류 편입)
└─ 운영 유의사항 안내
```

**개발 연동 노트**: 분류 마스터 테이블 + 항목-분류 참조. 삭제 시 참조 무결성 정책(공란 처리)을 서버에서 일관 적용.

## ADM-06 카테고리 관리 (AdminCategories, /admin/platforms)

**정의·역할**: 7개 카테고리의 메타 정보(표시명, 설명, 색, 아이콘, 외부 환경 URL)를 편집하는 화면. 전사관리자 전용.

**목적**: 신규 카테고리 추가나 명칭·브랜딩 변경을 개발 배포 없이(연동 후) 운영에서 처리하게 한다.

**기획 의도**: 카테고리 메타는 `CATEGORIES` 단일 소스이며 목록 필터·뱃지·통계 범례가 전부 여기서 파생된다. 즉 이 화면의 편집은 전 화면에 파급된다 — 그래서 전사관리자 전용이다. 아이콘·색상은 프리셋 레지스트리(아이콘 21종, 파스텔 팔레트 프리셋) 안에서만 고르게 해 톤앤매너 일탈을 막는다. 카테고리 간 유사색은 피한다(뱃지·범례에서 구분이 무너지므로 — 예: AI Model 바이올렛과 Vibe 핑크를 분리 배정).

**화면 동작**
- 목록에서 카테고리 선택 → 편집 패널에 메타가 로드되고 뱃지 미리보기가 표시된다.
- 색 프리셋·아이콘 프리셋을 고르면 미리보기가 즉시 갱신된다. 내부 id는 편집 불가(표시 메타만).
- 신규 카테고리 추가 시 id·경로 중복이 검사되어 중복이면 저장이 막힌다.
- 외부 환경 URL(`accessUrl`)이 비어 있으면 "미설정"으로 표기된다.

**지켜야 할 룰**
- 전사관리자 전용. 내부 id는 편집 불가.
- 색은 color(표기)/bg(배경) 쌍, 파스텔 프리셋 기반. 카테고리 간 유사색 회피.
- `accessUrl`은 카테고리의 외부 실행 환경 주소다(항목 URL 아님 — 0.5).

**화면 구조**
```
카테고리 관리
├─ 카테고리 목록 (7종 · 뱃지 미리보기)
└─ 편집 패널 (표시명/설명/색 프리셋/아이콘 프리셋/외부 URL)
```

**개발 연동 노트**: 연동 후에는 `CATEGORIES`를 서버 마스터로 이관하는 것이 목표(현재는 코드 상수, 화면은 시뮬레이션).

## ADM-07 조직 관리 (AdminOrg, /admin/org)

**정의·역할**: 관계사·부서 조직 정보를 관리하는 화면.

**목적**: 담당자 소속 표기, 승인 슬롯 자격 판정, 통계 축(참여 부서)의 기준 데이터를 정비한다.

**기획 의도**: 항목에 관계사를 표시하지 않더라도(0.5) 조직 마스터는 여전히 세 곳의 근간이다 — 승인 자격 판정(`managedCompanies`와 동일 코드 체계), 담당자 부서 표기, 집계 축. 관계사 노출 여부(visible)는 카탈로그 표시 범위를 통제하는 접근 게이트다: 비노출 관계사의 항목은 해당 소속이 아닌 일반 사용자에게 보이지 않는다.

**화면 동작**
- 관계사 목록에서 노출 여부를 토글 → 사용자 화면의 목록·통계 노출 범위가 바뀐다(접근 게이팅).
- 부서 추가·수정 → 담당자 소속 선택지와 통계 축에 반영된다.

**지켜야 할 룰**
- 관계사 코드는 승인 슬롯 자격·`managedCompanies`와 동일 체계 유지.

**화면 구조**
```
조직 관리
├─ 관계사 목록 (코드 · 명칭 · 노출 여부)
└─ 부서 관리
```

**개발 연동 노트**: 조직 변경은 기존 항목의 부서 표기 정합에 영향 — 변경 이력 관리 권장.

## ADM-08 사용자·권한 관리 (AdminUsers, /admin/users)

**정의·역할**: 사용자 목록 조회와 관리자 권한(부여·회수·범위 지정)을 관리하는 화면.

**목적**: 2-tier 권한 체계(0.6)를 운영에서 안전하게 집행한다.

**기획 의도**: 역할을 늘리는 대신 Admin의 범위(global/company)로 구분하는 0.6의 설계를 그대로 집행하는 화면이다. **전사관리자 최소 1명 가드**는 "아무도 전체를 관리할 수 없는 상태"라는 최악의 운영 사고를 UI 차원에서 원천 차단하는 장치다. 감사 로그는 권한 변경의 책임 추적용이며, 과거 로그는 당시 사실 그대로 보존한다(현행 체계와 표기가 달라도 소급 수정하지 않음 — 이력의 원칙).

**화면 동작**
- 사용자 검색·선택 → 권한 부여 패널에서 범위(global/company)를 고른다. company 선택 시 담당 관계사 멀티셀렉트가 나타난다.
- 저장 → 대상 사용자의 역할·범위 뱃지가 갱신되고 활동 로그에 기록된다.
- 마지막 남은 전사관리자의 global 권한을 회수하려 하면 → 차단되고 사유가 안내된다.

**지켜야 할 룰**
- 마지막 전사관리자의 권한 회수 차단(UI + 서버 이중 검증).
- 범위 뱃지로 각 관리자의 권한 범위 가시화.
- 감사 로그 보존 — 소급 수정 금지.

**화면 구조**
```
사용자·권한 관리
├─ 사용자 목록 (검색 · 역할/범위 뱃지)
├─ 권한 부여 패널 (global/company + 담당 관계사 멀티셀렉트)
└─ 활동 로그
```

**개발 연동 노트**: 권한 변경 API는 최소 1명 가드를 서버에서 재검증. user-company 관리 매핑은 N:M 테이블.

## ADM-09 공지 관리 (AdminNotices, /admin/notices)

**정의·역할**: 공지사항·업데이트 소식을 작성·수정·삭제하고 고정(pinned)·노출(visible)을 토글하는 관리 화면. **전사 관리자(admin) 전용**. 여기서 관리한 소식이 랜딩 최신소식과 `/notices`(USR-10)에 노출된다.

**목적**: 운영 소식을 관리자가 직접 게시·정정하고, 노출 시점·강조(고정) 여부를 통제하게 한다.

**기획 의도**: 공지는 브로드캐스트 채널이므로(0.10·USR-10) 발신 권한을 좁게 둔다 — 전 사용자에게 보이는 안내를 아무나 손대면 신뢰가 무너지기 때문에 **전사 관리자 전용**으로 제한한다. 라우트 가드는 관계사 관리자도 통과시키되(`requireAdmin allowCompanyAdmin`), 화면 내부에서 관계사 관리자에게는 관리 UI 대신 "전사 관리자 전용" 안내만 렌더하고, 사이드바 메뉴 자체를 관계사 관리자에게 숨긴다(방어 이중화). 노출(visible)·고정(pinned)을 분리한 것은 "지금 보여줄지"와 "맨 위에 둘지"가 별개 결정이기 때문이다 — 초안을 비노출로 작성해 두었다가 시점이 되면 노출로 전환하는 운영을 허용한다.

**화면 동작**
- 좌측 목록(종류 필터 세그먼트: 전체/공지사항/업데이트) + 우측 상세/편집 패널. **DEMO 전용** — 목업(`NOTICE_MOCK_DATA`)을 로컬 state로 로드해 작성/수정/삭제·고정·노출 토글 흐름을 재현한다(AdminCategories와 동일 패턴).
- 신규 작성 → 편집 필드(종류 세그먼트·제목·본문·게시일·고정·노출) 입력 후 저장. 신규 ID는 `NOTICE-{YYYY}-{NNN}`(현재 연도 최대 순번 +1, 서버 발급 TODO).
- 게시일은 `YYYY.MM.DD` 형식 검증. 비편집 상태의 고정/노출은 즉시 토글로 반영된다.
- 관계사 관리자가 접근하면 관리 UI 대신 "전사 관리자 전용" 안내만 표시된다.

**지켜야 할 룰**
- 실질 전사 관리자 전용. 라우트는 `requireAdmin allowCompanyAdmin`로 통과만 허용하되, 화면 내부에서 `isCompanyAdmin`이면 안내만 렌더(관리 UI 비노출). 사이드바 메뉴는 관계사 관리자에게 숨긴다.
- 편집 필드: 종류(공지사항/업데이트) · 제목 · 본문 · 게시일(`YYYY.MM.DD`) · 고정(pinned) · 노출(visible).
- 신규 ID는 `NOTICE-{YYYY}-{NNN}` 형식(서버 발급 대상).
- 2~3개 값 선택은 닫힌 드롭다운 대신 세그먼트 버튼을 쓴다(종류·필터·고정/노출 편집 공용 — 코딩 규약).
- 사용자에게 노출되는 표시 규칙(visible=true·pinned 우선·최신순)은 USR-10·랜딩과 동일 헬퍼를 따른다.

**화면 구조**
```
공지 관리
├─ 좌: 소식 목록 (종류 필터 세그먼트 · 고정/노출 상태)
└─ 우: 상세/편집 패널
   ├─ 종류(세그먼트) · 제목 · 본문
   ├─ 게시일 (YYYY.MM.DD)
   └─ 고정 · 노출 토글 + 저장/삭제
```

**개발 연동 노트**: 관리자 전체 목록(비노출 포함)은 `GET /api/v1/admin/notices`, 작성·수정·삭제는 `POST/PUT/DELETE /api/v1/admin/notices(/:id)`. 사용자 공개 목록은 별도로 `GET /api/v1/notices`(visible=true만, USR-10). 서버는 ID 발급·게시일 검증·권한(전사 관리자) 재검증을 담당한다. Notice는 알림을 발생시키지 않는다(0.10 확정).
